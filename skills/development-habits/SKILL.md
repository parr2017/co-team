# 开发习惯（Development Habits）

## 概述

规范 agent 开发行为的综合纪律手册：**每个动作可追溯、每个结论有证据、每次变更经用户确认**。既承载适用于任何项目的通用开发工作流纪律，也承载本项目（Viza：Vue3 + Element Plus）的 UI 设计规范与前端实现流程。**流程强度按改动规模分级执行**（见第 1 章），不因小修复套全套流程、也不因大改动偷工减料。

## 一句话骨架

> 规划落盘 → 逐步勾选 → 改前审查 → 改后验证 → 文档同步 → 测试留证 → 提交请示

---

## 1. 工作流纪律

1. **先定档级，再定流程**：任务开始前先按**影响面**判定流程档次（**影响面优先于代码量**：几行代码若碰公共对象/接口签名，依然按高档走）：
   - **A 轻量修复**：单文件、几行代码、不涉及公共对象（模型/DTO/VO/接口签名）、无数据库结构变更、无前后端联动。流程：一句话说明改哪/为什么 → 改 → 编译验证 → changelog 补一行。
   - **B 标准改动**：多文件、涉及 DTO/VO/接口签名、前后端联动等。走完整流程：任务进度表 + 影响分析审阅 + 小步验证 + 测试留证 + 文档同步 + 提交请示。
   - **C 重型/高风险**：大范围重构、删改、数据库结构变更、架构级调整。B 档全部 + 迁移/补丁脚本留痕 + 逐项用户确认。
   - 档级判定的底线动作：凡改动涉及公共对象，先全局检索引用处（grep），任何档级都不省略。
2. **先规划、后动手（B/C 档）**：B/C 档任务第一步是产出可追踪的执行清单（任务进度表），细化到每个文件、修改内容与状态；A 档跳过进度表，但 changelog 一行记录不可省略。
3. **单步原子化推进**：拆成小步骤，完成一步、验证一步、标注一步，再进入下一步。禁止并行堆改、禁止回头修改已标注完成的结论。
4. **断点续传**：B/C 档进度必须落盘（进度表/文档）。重启会话时先查当前未完成项接着做；A 档短平快、通常一次完成，中断时按"一句话说明"的起点恢复即可，无需落盘。上下文不完整时主动向用户确认，不臆测。

> 进度表模板见 `templates/progress-table.md`。

---

## 2. 改动规范

1. **改前全局影响分析**：动手前识别改动的关联对象（模型/DTO/VO/接口/引用处），列出全部受影响文件、位置与原因，给用户审阅同意后再改。判定标准为**影响面优先于代码量**：B/C 档列正式受影响清单给用户审阅；A 档轻量修复以一句口头说明（改哪、为什么改）替代正式文档。
2. **小步验证**：每轮改动后必须编译/语法通过（类型错误、引用缺失是最常见问题）。**A 档也必须给出验证证据**，不因改动小而省略。涉及前后端时，后端先完成并测试，再写前端。
3. **宁可复现也不臆断**：遇到行为不符合预期，先复现 → 定位 → 修复，不靠猜；修复后回归验证。

---

## 3. 文档即交付物

1. **代码与文档同步**：改代码必改对应文档；没有文档要先建，有文档要同步更新。
2. **版本化变更记录**：每次变更以版本号/日期归档（changelog），写明背景、改动内容、设计取舍、验证结果，保证历史可追溯。
3. **规范文档先行**：UI 规范、字段映射、接口契约、测试规范等单独成文，作为后续所有开发的唯一参照。

---

## 4. 数据库变更纪律

1. **变更留痕**：任何结构变更生成带注释的迁移/补丁脚本，注明何时、为何、改了什么，杜绝改库不留痕。
2. **不依赖强约束**：优先在应用层保证数据一致性，不随意使用数据库外键等强约束。

---

## 5. 测试纪律

1. **接口即契约**：接口/参数变化必须配自动化测试用例，通过才算交付。
2. **测试数据可隔离**：用时间戳等动态标识生成测试数据，避免冲突，测后清理。
3. **测试结论要证据**：通过/失败都要有明确输出（用例数、覆盖率、日志），不空口"应该没问题"。

---

## 6. 沟通与边界

1. **高风险操作先请示**：git 提交/推送、删除、大范围重构等，一律先询问用户，绝不擅自执行。
2. **变更前告知**：准备改哪些文件、为什么改、怎么改，先说明再动手。
3. **后台运行**：服务启动用后台方式，输出到日志文件，不阻塞主对话流。
4. **权限确认前置**：若检测到当前开发项目目录没有读写权限，主动询问用户是否需要为当前目录添加永久读写权限；经用户明确同意后才执行授权操作，绝不擅自修改系统权限。

## 7. UI 设计规范（Viza 项目）

> 本项目 UI 的唯一参照。UI_GUIDE.md 为完整版留档，与此章节必须保持一致；若两者冲突，以本 skill 第 7 章为准。

### 7.1 设计语言

**Visual Thesis**：沉稳的专业工具感，克制的蓝色单色系统，信息密度优先于装饰。

核心原则：
- **信息优先**：每个像素都应该帮助用户完成任务或理解信息
- **克制装饰**：能去掉的就去掉，能淡化的就淡化
- **品牌统一**：全应用只有一套蓝色体系，没有第二主色
- **组件一致**：相同功能使用相同组件，不混搭

风格关键词：专业 · 安静 · 高效 · 数据驱动 · Linear 式克制

### 7.2 色彩系统

全应用使用**单一的蓝色主色**，不允许出现偏离色（如 `#667eea`、`#2c3e50`、`#ffc107`）。

**主色**
```
--color-primary:        #1e3a8a    深蓝（品牌色，按钮、标题、侧栏）
--color-primary-hover:  #2563eb    亮蓝（hover 状态）
--color-primary-light:  #eef2ff    极浅蓝（背景、标签）
--color-accent:         #3b82f6    中蓝（链接、高亮）
```

**中性色**
```
--color-bg:             #f6f8fa    页面背景（极浅灰）
--color-surface:        #ffffff    卡片/面板/表单（纯白）
--color-border:         #e6edf4    标准分割线
--color-border-light:   #f0f4f8    更轻的分割线
--color-sidebar:        #0f172a    侧边栏（极深灰蓝）
```

**文字色**
```
--color-text:           #0f172a    主文字
--color-text-secondary: #64748b    次要文字
--color-text-tertiary:  #94a3b8    辅助文字/占位符
```

**状态色**
```
--color-danger:         #ef4444    危险/删除
--color-success:        #10b981    成功/完成
--color-warning:        #f59e0b    警告/进行中
```

**标签色（Tag）**——通过 `<el-tag>` 的 `type` 属性映射，不自定义颜色类：

| el-tag type | 视觉 | 语义 |
|---|---|---|
| `success` | 绿 | 成功/活跃 |
| `warning` | 黄 | 待审核/处理中 |
| `danger` | 红 | 失败/禁用 |
| `primary` | 蓝 | 系统/管理 |
| `info` | 灰 | 默认/无状态 |

### 7.3 排版系统

字体只用 Inter：`--font-family: 'Inter', -apple-system, BlinkMacSystemFont, 'Segoe UI', sans-serif`，不做多字体方案。

| 用途 | 变量 | 值 | 适用场景 |
|------|------|----|---------|
| 辅助 | --text-xs | 11px | 标签、版本号 |
| 正文小 | --text-sm | 13px | 表格内容、按钮、次要文字 |
| 正文 | --text-base | 14px | 段落、表单输入、消息内容 |
| 小标题 | --text-lg | 15px | 卡片标题、section 标题 |
| 页面标题 | --text-xl | 18px | 页面 h1、header 品牌名 |
| 大标题 | --text-2xl | 24px+ | 仅登录页使用 |

字重：正文/表格 400；按钮/标签/小标题 500；页面标题/品牌名 600；数字统计 700。

### 7.4 间距与圆角

间距（8px 网格）：`--space-xs:4px`、`--space-sm:8px`、`--space-md:16px`、`--space-lg:24px`、`--space-xl:32px`、`--space-2xl:48px`。

圆角：`--radius-sm:6px`（按钮、输入框、标签）、`--radius-md:10px`（卡片、对话框、表格）、`--radius-lg:16px`（外层容器、大对话框）。

阴影：`--shadow-sm:0 1px 2px rgba(0,0,0,0.04)`（卡片默认态）、`--shadow-md:0 4px 16px rgba(0,0,0,0.06)`（卡片 hover/对话框）。

### 7.5 组件规范

**7.5.1 按钮 —— 全部使用 `<el-button>`，禁止自定义 `.btn-*` 类，禁止原始 `<button>`**

| 语义 | 用法 | 视觉 |
|------|------|------|
| 主要（上传/新建/保存/发送） | `type="primary"` | 实心深蓝底白字 |
| 幽灵（编辑/下载/取消/返回） | `type="primary" plain` | 透明底，hover 出浅蓝背景 |
| 危险（删除） | `type="danger" plain` | hover 时变红色背景 |
| 小号 | `size="small"` | 紧凑尺寸 |

规则：同一行多个按钮时，只有最主要的一个用 `type="primary"`，其余用 plain；不出现黄色、绿色等非主色按钮；圆角统一 6px。

**7.5.2 表格 —— 全部使用 `<el-table>`，禁止原生 `<table>`**

- 表头：`#fafbfc` 极浅灰背景，文字 `--text-tertiary`，`font-weight:500`
- 表头与第一行之间用 `--border-light` 分割线；行间用极细分割线
- 禁用 `stripe` 属性（斑马纹过时）
- 顶部工具栏与表格分开，不混在一起

**7.5.3 对话框 —— 全部使用 `<el-dialog>`，禁止自定义 modal-overlay**

- 标题：`--text-lg`，`font-weight:600`
- 内容：标准 `--space-lg` 内边距
- 底部按钮右对齐：取消（plain）+ 确定（primary）
- 圆角阴影由 Element Plus 默认处理

**7.5.4 卡片**

默认无边框，hover 时显现边框和微阴影。仅在首页的工具/助手卡片和统计卡片中使用；**管理后台内部不使用卡片**。

**7.5.5 对话气泡**

| 角色 | 背景 | 文字色 | 圆角 |
|------|------|--------|------|
| 用户 (user) | `--color-primary` | #fff | 10px + 右下 4px |
| 助手 (assistant) | `--color-surface` + 1px solid `--border-light` | `--text` | 10px + 左下 4px |

气泡标签（"我"/"Viza"）11px，`opacity:0.65` 或 `--color-primary`。

**7.5.6 表单 —— 只用 `<el-form>`/`<el-input>`，不支持手动裸样式**

- 标签：13px，`font-weight:500`，`color:var(--text)`
- 输入框：`background:var(--bg)` / `border:1px solid var(--border)`
- focus：`border-color:var(--primary)` + `box-shadow:0 0 0 3px rgba(30,58,138,0.06)`

**7.5.7 标签 —— 全部使用 `<el-tag size="small">` + `type` 属性**，颜色映射见 7.2，不得自定义标签色。

**7.5.8 导航**

- **禁止 emoji 图标**，全部使用 Element Plus Icons 或 SVG 图标
- 侧边栏文字：非活跃 `rgba(255,255,255,0.55)`、活跃 `#fff`
- 活跃项背景：`rgba(255,255,255,0.1)` 或 `--color-accent`
- 图标 16x16，stroke-width:1.6

### 7.6 布局规范

**登录页**：浅灰纯色背景 `#f0f2f5`（无渐变、无白色卡片），品牌标识 + 一句话 + 两个输入框 + 一个按钮，表单居中最大宽度 340px。

**首页**：背景 `--bg`，header 白色，section 标题 13px 灰色；工具/AI 助手两个 section 各 3 列 grid；卡片默认透明边框 hover 显现。

**管理后台**：sidebar 200px（背景 `--sidebar` `#0f172a`）+ topbar 48px（白色+浅灰分割线）；内容区 padding `--space-lg`；统计卡片无边框纯文字排版；表格全宽。

**对话页**：topbar 48px（返回/标题/新对话按钮）+ 消息列表（用户右对齐、助手左对齐，消息最大宽度 72%，区域背景 `#fafbfc`）+ 底部固定输入区（textarea + 发送按钮，不随滚动）。

### 7.7 硬性规则

1. **全局只一个蓝色主色** `#1e3a8a`，任何页面不使用 `#667eea`、`#2c3e50` 等偏离色
2. **不接受任何 emoji** 出现在 UI 中，全部使用 SVG 图标或 Element Plus Icons
3. **不接受原生 `<table>` + 自定义 modal overlay**，全部使用 `<el-table>` + `<el-dialog>`
4. **所有按钮使用 `<el-button>`**，不再写自定义 `.btn-primary`/`.btn-edit`/`.btn-approve` 等
5. **不接受黄色按钮**（`#ffc107`），删除用红色，编辑用 plain，主要操作用蓝色
6. **CSS 变量全局化**：在 `frontend/src/style.css` 定义 token，各组件引用 `var(--xxx)`，不硬编码色值
7. **Cardless 优先**：管理后台不使用卡片包裹内容，section 直接使用纯色区块 + 分割线
8. **不接受全屏渐变背景**，含登录页（登录页统一纯浅灰 `#f0f2f5`）
9. **不接受两套组件体系**：同一功能在所有页面使用相同的 Element Plus 组件
10. **不接受斑马纹表格**：`stripe` 属性禁用

**UI 审核清单**（代码审查时逐项检查）：
- [ ] 是否有任何 `#667eea`、`#2c3e50`、`#ffc107`、`#e74c3c` 等偏离色？
- [ ] 是否有任何 emoji（🟢🔴🎭🔐👥📚🏠🤖💬🔧等）？
- [ ] 是否有原生 `<table>` 或自定义 modal overlay？
- [ ] 是否有自定义 `<button>` 没使用 `<el-button>`？
- [ ] 是否所有组件引用 CSS 变量而非硬编码色值？

## 8. 前端实现流程（走 frontend-skill）

1. **凡 UI/页面/组件开发任务，必须先加载并使用 `frontend-skill` 技能**。UI 设计与实现遵循本 skill 第 7 章（设计令牌/组件体系）+ `frontend-skill`（构图/层级/动效/克制审美）双轨约束。
2. **动手前先写三件事**（Working Model）：
   - visual thesis：一句话描述情绪、质感与能量
   - content plan：hero → support → detail → final CTA
   - interaction thesis：2-3 个改变页面感觉的动效想法
3. **Beautiful Defaults 约束**：先构图再组件；品牌/产品名是最大文字；文案短到数秒可扫读；优先用留白/对齐/缩放/裁切/对比，而非花哨装饰；两套字体上限、默认一种强调色；默认无卡片布局（用 section/列/分割线/列表/媒体块）；首屏视作海报而非文档。

## Red Flags 自查表（出现即停下纠正）

| Red Flag | 正确做法 |
|----------|----------|
| 小修复（A 档）却套全套流程：先建进度表 + 正式影响分析文档 + 全套测试 | 按 A 档轻量执行：一句话说明 → 改 → 编译验证 → changelog 一行；保住验证与提交纪律即可 |
| 直接写代码，没先建任务进度表 | 先判断档级：B/C 档先规划落盘再动手；A 档走轻量流程 |
| 一个步骤没标注完成就进入下一步 | 原子化推进，完成一个标一个 |
| 没让用户审阅就大改 | 改前列出受影响文件与原因，征得同意 |
| 跳过编译/语法验证就声称完成 | 前后端都必须编译通过 |
| 改了代码但没同步文档/changelog | 文档即交付物，必须同步 |
| 接口变了却没写测试 | 接口即契约，测试通过才算交付 |
| 想直接 `git add/commit/push` | 先请示用户，经同意再执行 |
| "应该没问题" / "我猜是..." | 复现并拿出证据，不臆断 |
| 启动服务占着对话框 | 后台运行，日志落盘，只看日志 |
| 对无读写权限的目录直接读写 | 先询问用户是否为当前目录添加永久读写权限 |
| 写了原生 `<table>` / 自定义 modal / 自定义 `.btn-*` / emoji / 偏离色 / 两套组件体系 | 违反第 7 章 UI 硬性规则，按统一标准（el-table/el-dialog/el-button）整改 |
| 写前端 UI 时没先走 frontend-skill | 违反第 8 章，先加载 frontend-skill 再动手 |

## 常见失误

- **改模型只改一处**：修改实体/DTO/VO 时必须全局检索所有引用处，否则编译/运行时炸。
- **测试数据污染**：固定编号的测试数据互相干扰，必须用动态标识并清理。
- **进度表与实情脱节**：禁止提前标注未完成任务；任务中断时如实保留未完成状态，恢复后继续。

## 使用提示

- 本 skill 是**流程纪律 + Viza 项目 UI 规范**，不替代具体技术方案的 skill；与 TDD、systematic-debugging、frontend-skill 等过程/实现类 skill 可配合使用。
- 第 7 章为 Viza 项目 UI 令牌与组件体系的唯一参照，与 `UI_GUIDE.md` 保持一致（冲突时以本 skill 第 7 章为准）。
- 第 8 章要求：任何前端 UI 任务先加载 `frontend-skill`，再结合第 7 章落地。
- 进度表模板位于 `templates/progress-table.md`，可复制到任务根目录按需填写。
