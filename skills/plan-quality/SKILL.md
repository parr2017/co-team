# 计划质量规范（Plan Quality）

## 定位

本 skill 管"**怎么把计划出好**"，不管执行纪律（执行、验证、留痕见 `development-habits`）。两者配合：本 skill 产出计划 → development-habits 按计划执行。档级口径（A/B/C）与进度表模板保持一致。

一份好计划满足五条：**先调研后规划、结构完整、每步可验证、落盘可追踪、外行能看懂**。

---

## 1. 何时必须出计划

满足任一条件就出计划，不要等用户点名：

- 用户明确要求：出计划 / 出方案 / 拆解任务 / 排期 / 评估工作量 / "这个怎么做"
- 任务超过 3 步，或要改多个文件
- 涉及公共接口、数据结构、删改操作、外部系统、前后端联动
- 执行中发现计划缺失或失效（见第 7 节）

### 计划深度与任务规模匹配

计划深度跟着**影响面**走（口径同 development-habits 的 A/B/C 档，影响面优先于代码量）：

| 档级 | 典型场景 | 计划形态 |
|---|---|---|
| 微型（A 档） | 单文件几行改动、不碰公共对象、无结构变更 | 一句话计划：解决什么问题 + 改哪 + 为什么 + 怎么验证。不落盘 |
| 标准（B 档） | 多文件、涉及接口签名、前后端联动 | 完整计划（八要素）+ 落盘 |
| 重型（C 档） | 大范围重构、删改、数据库结构变更、架构调整 | B 档全部 + 风险回滚细化 + 逐项用户确认 |

底线：**小任务不套全套文档**（A 档任务写一份八要素计划是浪费双方时间），**大任务不偷工减料**。凡涉及公共对象，计划前先全局检索引用处，任何档级都不省略。

---

## 2. 前置调研：先搞清楚，再排步骤

不了解现状就出计划 = 臆测，臆测的计划执行时一定翻车。出计划前先读相关代码、文档、数据。

计划里的信息分三类，必须显式区分：

- **已确认事实**：附证据（文件:行号、命令输出、文档原文）
- **假设**：标注"假设，待验证"，并写明怎么验证
- **未知**：需要进一步调研，或直接问用户

关键歧义**先问用户**，不要基于猜测出一份看起来很确定的计划。优先调研有没有可复用的现成实现（工具函数、既有模式、既有组件）——重复造轮子的计划是坏计划。

探索性任务（结论依赖调研结果）要标注探索性：先列"要探明什么"，探明后再细化后续步骤，不要伪装成确定计划。

---

## 3. 标准计划结构（八要素）

B/C 档计划按八要素组织，模板见 `references/plan-template.md`：

1. **背景与目标**：解决的是什么问题、用户要什么、做完怎么算成功（可验收的标准）
2. **现状与约束**：相关文件/模块现状、已有实现、限制条件（不能动的、依赖的、时间限制）
3. **方案与取舍**：存在多种可行做法时，列对比（做法/优点/代价/风险）+ 明确推荐及理由；只有一种做法时，说明为什么不考虑别的
4. **影响面**：受影响的文件、接口、数据、文档清单
5. **步骤分解**：每步 = 做什么 + 改哪个具体文件 + 怎么验证（命令/方式/预期输出）。单步原子化：一步可独立完成、可独立验证
6. **风险与回滚**：哪些地方可能翻车 + 翻车了怎么办；高风险变更给具体回滚步骤
7. **决策点**：需要用户拍板的地方显式标出，给默认选项和备选，不替用户默默决定
8. **交付物清单**：代码、测试、文档、changelog

## 4. 说人话：输出可读性规范

计划的第一读者是用户，默认用户不是领域专家。术语堆出来的计划，用户看不懂等于没出。

### 人话摘要（计划开头必须有）

10 秒能读完的一段话，按顺序回答：

1. **解决什么问题**
2. **做什么**
3. **怎么做**（一句话概括）
4. **做完后效果是什么**

技术细节放后面，别用细节开头。

### 四问框架

每个部分、每个步骤都按四问组织，缺一问就补：

| 四问 | 回答什么 |
|---|---|
| 解决什么问题 | 针对哪个具体问题、动机是什么 |
| 做什么 | 动作本身，一句话说清 |
| 怎么做 | 具体到文件、命令、操作方式 |
| 为什么 | 为什么这么改、为什么不选别的做法 |

示例对比：

❌ 坏步骤：

> 3. 优化数据层
> 4. 完善导出逻辑

✅ 好步骤：

> 3. 在 `backend/service/export.py` 改成分批查询、逐批写入文件。
>    **为什么**：现在是一次性把全部数据读进内存再生成文件，数据量大时会内存爆掉；分批写入把内存占用从"全部数据"降到"一批数据"。
>    **验证**：用 10 万行数据跑一次导出，内存峰值 < 500MB，导出文件行数 = 100000。

### 术语纪律

- 术语/缩写第一次出现，顺带一句大白话解释，如"DTO（前后端之间传数据的格式约定）"，后文可以直接用
- 能用日常语言就不用术语：写"把返回的时间统一成 2026-01-01 这种格式"，不写"格式化时间戳为 ISO 8601"（除非后者就是需求本身）
- 不写空话套话："赋能""优化整体体验""完善架构"——把专业词删掉后信息量为零的句子，删掉或重写

### 语言习惯

- 一句话一个意思，不写多层嵌套的长句
- 复杂概念配一个具体例子或类比
- 自检方法：假设读者不懂技术，通读计划——每一步能不能看懂"在干嘛、为什么干"？看不懂的地方就是没写清楚的地方

## 5. 质量自检清单（出完计划必过一遍）

- [ ] 开头有人话摘要（解决什么问题 → 做什么 → 怎么做 → 效果）？
- [ ] 每一步都有"怎么算完成"的验证方式？
- [ ] 文件/接口/命令具体到路径？（出现"相关文件""适当调整"即不合格）
- [ ] 每步四问齐全（解决什么问题/做什么/怎么做/为什么）？
- [ ] 术语首次出现都有解释？没有空话套话？
- [ ] 假设显式标注，没有混进事实里？
- [ ] 步骤原子化（单步可独立完成 + 验证）？
- [ ] 风险与回滚有着落？
- [ ] 需要用户拍板的决策点标出来了？
- [ ] 计划深度与任务规模匹配？（A 档没套全套，B/C 档没偷工减料）
- [ ] 探索性部分标明"先探明再细化"，而不是伪装成确定计划？

---

## 6. 落盘与追踪

- B/C 档计划落盘为 Markdown 文档（放任务相关目录，命名带任务名和日期）
- 步骤表带状态列，执行时完成一步勾一步（进度表模板复用 `development-habits/templates/progress-table.md`）
- 断点续传：重启会话先读计划，找未完成项接着做，不重新规划
- 禁止提前勾选；中断时如实保留未完成状态

---

## 7. 偏差维护：计划是活的

- 执行中发现现实与计划不符：**先更新计划**（改了什么、为什么改），再继续执行。与实情脱节的计划比没有计划更糟
- 范围变化（比计划多做了 / 少做了 / 发现新问题）：回到用户确认，不擅自扩权
- 已完成的步骤不回头改结论；未完成的如实标注

---

## 8. Red Flags 自查表（出现即停下纠正）

| Red Flag | 正确做法 |
|---|---|
| 空洞步骤（"优化代码""完善逻辑"） | 拆到具体文件 + 具体改动 + 验证方式 |
| 不调研就排步骤 | 先读代码确认现状，事实/假设分开标注 |
| 步骤没有验证方式 | 每步给"怎么算完成" |
| 一步跨 10 个文件 | 拆成可独立验证的原子步骤 |
| 通篇术语黑话，用户看不懂 | 术语首现即解释，每步按四问来写 |
| 开头就是技术细节，没有问题背景 | 计划开头先给人话摘要 |
| 多方案存在却只给一个、不给理由 | 列对比 + 推荐理由；唯一方案说明为什么 |
| 探索任务写成确定计划 | 标注探索性，先探明再细化 |
| 小任务套全套计划文档 | 按档级：A 档一句话计划 |
| 高风险计划不等确认直接开干 | 涉及删改/公共接口/数据结构，先请示 |
| 执行漂移不更新计划 | 偏差即更新计划并说明原因 |
