## 〇、先看懂五个背景概念

后面的所有方案都建立在这几个概念上，先用大白话讲清楚。

**1. 模型池（model pool）**
系统不绑定某一个 AI 模型，而是维护一个"池子"（`config/config.yaml` 的 `model_pool`，当前 10 个模型）。每个模型有三样属性：健康分（最近失败越多次序越靠后）、优先级（priority）、专业度（professional_weight）。派活时按任务难度选模型，坏了就换下一个——这是"模型不可用自动替换"的基础。

**2. 任务车道（lane）**
任务不是来了就跑，而是先进队列。队列按"车道"分组：**同一车道一次只跑一个任务，不同车道可以同时跑**。车道现在按"项目 id"划分——绑定同一个项目的任务排同一条队。这是目前"全串行"感觉的来源（详见问题 5）。

**3. 任务内 DAG 并行**
一个任务内部由规划器拆成多个节点（如：设计接口 → 实现接口 → 写测试），节点之间有依赖关系（edges）。**没有依赖关系的节点本来就会同时执行**——所以"并行"不是从零做，任务内早就有了；缺的是任务与任务之间的并行。

**4. 事件流（event stream）**
执行过程中发生的每件事（节点开始/完成、模型切换、命令待审批、留言……）都会发一条"事件"，web 和 mobile 界面的事件流、作战室会话流就是靠它实时刷新的。**要让某个东西"在界面上看得见"，标准做法就是给它发一条事件 + 两端加一条中文文案映射。**

**5. 技能（skill）注入机制**
技能 = `skills/` 目录下的 SKILL.md 文件（现有 16 个）。执行节点时，系统只把**技能目录（名字+一句话描述）**塞进给模型的提示词（为了省 token 和保住推理服务的前缀缓存），**正文不塞**；模型判断"这个技能和我的活相关"，就主动调用 `load_skill` 工具把正文拉进对话。所以技能生效分两步：索引注入（系统做的）→ 正文拉取（模型做的）。模型不拉，技能就不生效。

## 一、六个问题的现状解答

### 问题 1：模型不可用时，系统怎么替换模型？

**一句话结论**：有完整的多级替换机制，全自动，且每一步都发事件、可回溯。

替换链条（从轻到重）：

| 层级 | 触发条件 | 动作 |
|---|---|---|
| 健康度熔断 | 某模型连续 ≥3 次失败 | 冷却 1→5→15 分钟（指数退避），期间不再选它 |
| 容量避让 | 同一服务端点返回 429（限流） | 该端点整组避让 60 秒 |
| 降级阶梯 | 当前模型调用确定性失败（连接死亡、流假死） | 记失败分 → 发 `model_failover` 事件 → **自动换链上下一个健康模型重试** |
| 分型处理 | 413 上下文超限 | 不换模型，先折叠历史压缩上下文重试一次，再按上下文长度重排降级链 |
| 分型处理 | 429/503 | 不换模型，同模型退避 20s/40s 重试两次 |
| 主 Agent 接管 | 普通节点重试耗尽 | 升级给主 Agent 模型接手该节点 |
| 破窗兜底 | 主 Agent 接管也因模型不可用失败 | 无视冷却，从池里挑任何活着的模型做最后一次尝试 |

**在哪能看到**：界面事件流里的 `model_failover`（模型切换）、`model_slow`（慢成功）、`llm_backoff`（退避重试）；web 设置里的模型池面板可看每个模型的实时健康分/冷却状态；任务中途可手动换主模型（`PUT /api/tasks/:id/model`）。

### 问题 2：命令白名单在哪里配置？

**一句话结论**：分三层，你界面上没找到的是"全局缺省"这一层——它目前**没有界面**，只能改配置文件。

| 层级 | 在哪配 | 生效范围 |
|---|---|---|
| 全局缺省 | `config/config.yaml` 的 `permissions.level` + `permissions.whitelist_commands` | 所有任务（当前需重启生效） |
| 任务级（创建时） | web 创建任务表单 / mobile 创建页，选权限级别+白名单 | 单个任务 |
| 任务级（执行中） | web 任务详情对话框改策略、预检缺白名单一键补授、命令审批卡片；mobile 审批收件箱 | 单个任务 |

权限级别共五档：`plan_only`（只准规划）→ `readonly`（只读）→ `approve_required`（白名单外命令一律人工审批）→ `whitelist_auto`（白名单内自动放行）→ `full`（目录内完全控制）。高危命令（删库、`git push`、内联解释器代码等 SEC-P0 形态）**任何级别都强制人工审批**，目录监狱（越界路径拒绝）任何级别都生效。

**发现的隐患**：当前 `config.yaml` 里写的是 `level: normal`——这不是合法值，运行时只能静默回退成 `whitelist_auto` 并反复刷告警日志。等同于"配置写错了但系统替你兜底"，不可见、易误解。

### 问题 3：agent 执行时 skill 有没有生效？在哪能看出来？

**一句话结论**：生效与否的数据一直在记录，但 web 上只有一张不显眼的卡片，mobile 上完全没有。

判定方法（按可靠度排序）：
1. **web 任务详情 → 点开节点 → "执行档案"卡**：有两行关键字段——`skills_indexed`（这次执行注入了哪些技能索引）和 `skills_loaded`（模型实际调 load_skill 拉了哪些正文）。**前者是"发了牌"，后者是"真的用了"**。文件位置：`web/src/components/TaskDetailDialog.vue:149-171`。
2. **会话回放**（web 任务详情 → 完整会话回放）：翻工具调用轮次，能看到 `load_skill` 的调用和返回的正文。
3. **服务器日志**：`logs/co-team-*.log` 里 grep `Skills loaded for node`。

为什么模型可能"不拉"：注入的只是索引，模型自主判断相关性。任务描述与技能描述关键词不重叠、或模型能力弱时，就不会拉。想提高命中率：把技能的 description 写得更贴合任务常用词，或在 agent.yaml 里直接绑定（绑定技能的索引会带"必须先拉取"的强提示）。

### 问题 4：近期任务成功率不高，差在哪？

**数据**（来自 Redis 全量 52 张任务图）：终态任务 46 个，成功 23 个，**成功率 50%**；节点级完成率 79.4%（350 节点完成 278，其中 51 个是被上游失败连带的取消）。

失败原因分布（09-03 → 09-15）：

| 原因 | 数量 | 现状 |
|---|---|---|
| 规划器崩溃 `Invalid array length` | 5 个任务连败（09-14 深夜起） | **已修复**——根因是知识库条目"转义翻倍"膨胀出 193MB 怪兽文件，拖垮读取管线；09-15 早上 701aae9 提交加了体积门+对称反转义。但规划链路仍缺"守卫"（见包 A） |
| 前置缺失转人工 | 4 例（沙箱里没有预期文件/项目） | **治理中**——昨天的"任务级环境预检"commit 就是让计划在发车前对齐环境事实 |
| LLM 输出无法解析 | 5 例（集中在 09-03 早期） | 旧问题，后续未见复发 |
| 网关错误/超时（502/504/流停滞） | 若干 | 已有自动分型重排（infra 类 1/5/15 分钟自动重排，上限 3 次） |
| 上游失败连带取消 | 51 节点取消 | 属正常 DAG 行为，根因在上游 |

**结论**：50% 是"修复前"的数字，两个大头（规划崩溃、前置缺失）已在修复路径上。本轮包 A 再把规划链路对脏数据免疫补上，成功率应有实质性回升。

### 问题 5：为什么感觉全是串行？怎么提速？

**一句话结论**：任务内部早就并行；串行发生在"任务与任务之间"，根因是队列车道的设计，且已有现成改造方案。

- 任务内：DAG 连续调度器（`runGraph`），无依赖节点同时跑，并行度上限 = 模型池总空闲槽位（约 20+ 槽）。
- 任务间：车道单槽位（`Lane.running` 一次只放一个任务）+ **车道键只看项目 id**——没绑项目的任务全挤进同一条 `default` 车道，哪怕它们的工作区（目录）完全不同、八竿子打不着。这是**纯损失**：不同工作区的任务本来互不干扰，却被迫排队。

**长任务规划**已有 M4 滚动规划：先把任务拆成"可运行的最小骨架"（第 1 阶段）+ 全局验收清单，跑完一阶段再规划下一阶段（每阶段 ≤5 节点），不用一次性规划到底。

**提速方案**：落地并行改造 Phase 0-2（见包 B）。Phase 1 完成后，不同工作区的任务立即并行；同工作区（同一项目）内仍串行——这是**故意的安全设计**：任务收尾要把成果回写工作区、跑验收、动 git HEAD，同工作区并行会互相踩踏（技术细节见实施计划文档 §1.2：回写互抹、HEAD 竞争、验收互踩三坑）。

### 问题 6：agent 之间到底有没有沟通？

**一句话结论**：机制有五条通道，一直在工作；但界面只露出了一小半，你看不见的部分恰恰是最重要的部分。

| 通道 | 机制 | 界面上可见吗 |
|---|---|---|
| 留言 `send_message` | agent 发给其他 agent，收件方**下次执行时**注入提示词 | 发送方有作战室留痕和事件；**接收方收到后无任何痕迹** |
| 问答 `ask_agent`/`ask_user` | 阻塞式提问，等答复再继续 | 有 `ask_created` 等事件，双端可见 |
| 上游交接 | 下游节点自动继承上游节点的成果摘要和变更清单（注入提示词） | **完全不可见**——纯提示词注入 |
| 协同文档 | SSOT 文档（TASK_SPEC/API_CONTRACT 等），版本化 | 有 `doc_updated` 事件 |
| 群组讨论 | 多 agent 群聊引擎，可转任务 | 有独立界面 |

所以你"没看见"的判断是对的：**接收方收到留言后的消化、上下游之间的接力传递，都发生在提示词里，界面无感知**。包 C 就是把这些全部事件化。

## 二、四个改进包

### 包 A：稳定性加固 —— 让"小故障"不再杀死"主流程"

**解决什么问题**
9-14 深夜的 5 连败暴露了一个结构性弱点：规划主流程（读记忆、读知识库、调模型、出计划）里，**辅助数据的读取没有任何容错**。知识库/历史经验属于"锦上添花"的数据，它们损坏时正确行为应该是"没有经验就没经验，照样规划"，而不是整个任务失败。另外 `permissions.level: normal` 这个非法值说明配置缺合法性兜底提示。

**做什么（4 件事）**
1. 修正 `config/config.yaml` 的 `level: normal` → `whitelist_auto`（这是运行时配置文件，不入库，直接改）。
2. 给规划链路加守卫：`server/src/orchestrator/planner.ts` 中，`llmPlan` 函数的 try 块只包住了"调模型"那一段，**读记忆（getMemory）和读知识库（relevantKnowledge）裸奔在 try 外面**（planner.ts:215-216）；滚动规划的 `generateStagePlan`（:264-313）则整段无守卫。把这两处读辅助数据的调用包上 try，失败时降级为"空记忆、空知识"继续规划。
3. 失败日志补堆栈：`planStage1` 的 catch（orchestrator.ts:466）和 `failGraph`（:701）目前只记 `String(e)` 一行文字，下次再出怪错查不到位置；补记 `e.stack` 前 10 行。
4. 回归测试：单测里植入坏知识条目（超大文件、坏 frontmatter），断言 `generateTaskGraph` 仍能产出计划（哪怕退回线性兜底图）。

**为什么这么做**
- 守卫加在"读取处"而不是"调用处"层层包：改动最小、语义清晰——只有读辅助数据才允许降级，调模型失败仍走既有的模型池换模逻辑，两套语义不混淆。
- 不选"修好知识库写入就一劳永逸"：701aae9 已修根因，但防御纵深原则要求"就算再出一种新的损坏方式，主流程也不能死"。本次 5 连败的教训正是缺了这层。

**怎么验证**：跑单测（坏数据不崩）；造一条坏知识条目后创建测试任务，任务正常出计划；启动日志不再出现 `level` 告警。

### 包 B：并行提速 —— 不同工作区的任务立即并行（Phase 0-2）

**解决什么问题**
（1）自指任务（用 co-team 开发 co-team）隔离失效的 P0 正确性 bug；（2）不同工作区任务被迫串行的纯损失；（3）并行放开后会被放大的三个隐患（内存、读放大、模型池争抢）。

#### Phase 0：自指隔离修复（正确性 bug，先行）

**问题**：自指任务本应隔离到 `projects.selfdev_root/<taskId>` 的独立克隆里执行，主仓库"零触碰"。但 `execute()` 里只有 `graph.workspace` 换成了克隆路径，**创建沙箱、回写成果、验收、git 提交用的仍是原始入参（co-team 主仓库路径）**——首次执行的自指任务会直接写主仓库工作树。这不是理论风险：工作树里已发现与该形态吻合的遗留改动。

**做什么**：`orchestrator.ts` execute() 在克隆准备完成后，统一用本地变量 `workspace = execWorkspace`，让沙箱创建与全部收尾动作都指向克隆路径；补一个回归测试（假主仓库 + self_ref 任务，断言所有落盘目标都是克隆路径）。

**为什么先行**：它是正确性 bug；同时"多个自指任务各自克隆、天然互不干扰"正是将来并行的基础。

#### Phase 1：车道键按 workspace（并行主体）

**做什么**：`taskQueue.ts` 的车道键从"项目 id"改为"规范化工作区路径"（`ws:<path>`，大小写/斜杠归一）。绑定了项目的任务映射到其工作区的键——保证"同项目⇒同工作区⇒同车道"的串行保护不被绕过。队列快照增加 `workspace` 字段；web `QueuePanel` 与 mobile `TaskListView` 的车道标签同步支持"工作区队列"显示。

**效果**：不用任何新配置，不同工作区的任务立即并行；同工作区维持串行（安全不变）。

**为什么这样改**：串行的真实工程约束是"同工作区收尾会互踩"，那就让"互踩的可能"本身（同工作区）作为互斥单位，而不是用更粗的"项目"近似它。改动集中在 keyFor 一个函数 + 展示层，零迁移成本（车道状态纯内存，重启即重建）。

#### Phase 2：并行加固（并行能稳住不炸）

1. **stdout 封顶**：`sandbox.ts` 异步命令执行的输出目前无界累积（同步版有 8MB 上限，异步版没有）——历史上两次 4GB OOM 事故的隐患之一。改为滚动截尾、各保留尾部 1MB。
2. **知识库缓存+互斥**：现在每次派发节点都全量读 111 个知识文件、命中计数还要读-改-写回写——并行任务 ×N 后是读放大+互踩窗口。加 mtime 缓存（文件没变就读缓存）+ 进程内互斥锁。
3. **模型池公平分配**：单任务的节点并行度当前 = 全池总槽位，能把模型池吃干；两个任务并行时会互相抢槽、放大 429 风暴。改为 `maxWorkers = floor(总槽位 / 活跃任务数)`，单任务时行为不变。
4. **双端多任务展示**：web 首页现在只显示第一个活跃任务（`ActiveTaskHero.vue`），并行了其余任务在首页不可见。改为 hero + "另有 N 个任务并行中"徽标；mobile 队列区同步多任务展示。

**为什么 Phase 2 是"必须"而不是"可选"**：并行把所有共享资源的压力乘以任务数。不加固就开并行，等于把历史上治理过的 OOM/429 风暴重新引入，只是触发概率更高。

**怎么验证**：三个新队列测试用例（不同 workspace 并行 / 同 workspace 串行含绑不绑项目混用 / 原跨项目用例保持绿）；公平分配单测；双端构建 + **移动端实拍**（8857，AGENTS.md 硬性要求）；跑两个不同工作区的任务实测同时执行。

### 包 C：Agent 协作可视化 —— 把"看不见的沟通"搬到界面上

**解决什么问题**
问题 6 揭示的三个盲区：接收方收到留言无痕迹、上下游交接无痕迹、（留言依赖模型主动调用所以本来就少）。目标是让每一次 agent 间的信息流动都在作战室里有一条可读记录。

**做什么**
1. **接收侧事件化**（server）：`orchestrator.ts:2910` 消费留言处，每条收到的留言追加一条作战室 journal（"收到来自 X 的留言：……"）+ 发一条事件（`agent_message`，kind=received，带发送方和摘要）。
2. **交接事件化**（server）：节点派发时，把注入给下游的"上游成果摘要/变更清单"落一条 journal + 发 `node_handoff` 事件（文案如"接力自「实现登录接口」：接口已完成，改动 3 个文件"）。
3. **web 协作卡片**（`web/src/components/ChatStream.vue`）：留言/收到/交接渲染成醒目的协作卡片（from→to 样式），与普通消息区分；节点详情加"上游交接"区块展示注入了什么。
4. **mobile 对齐**（`mobile/src/components/ChatStream.vue` + 两端 `utils/events.ts`）：同构协作卡片；事件中文映射补 `agent_message(received/doc)`、`node_handoff`。

**为什么选"事件+卡片"而不是新做一个协作总览页**：事件流是系统现成的实时管道，两端会话流组件同构，改动小、双端天然一致；协作记录混在作战室时间线里恰好符合"看战况"的阅读习惯。独立总览页等用一段时间后再评估是否需要。

**怎么验证**：跑一个多节点任务，web/mobile 的作战室里能看到完整的"发送→接收→接力"链；两端事件流对每个协作事件都有中文文案。

### 包 D：白名单 + 技能可观测 UI —— 把"改配置文件"变成"点界面"

**解决什么问题**
（1）全局命令白名单没有界面（问题 2 的直接痛点）；（2）mobile 上完全看不到 skill 是否生效（问题 3），也没有模型池等设置能力。

**做什么**
1. **新增全局权限 API**：`GET/PUT /api/config/permissions`（读写 config.yaml `permissions` 节），级别做合法值校验——从根上杜绝再出现 `level: normal` 这类写错值静默回退。
2. **web 设置**：`SettingsDialog.vue` 增"命令权限"分区——级别下拉（五档中文名）+ 白名单命令标签编辑器（复用创建表单的输入模式）。
3. **mobile 设置**：新增简版权限分区（级别展示+白名单查看/编辑，Vant 风格）。
4. **mobile 执行档案卡**：`TaskDetailView.vue` 节点展开区补齐与 web 对齐的执行档案（轮次/耗时/工具统计/**skills_indexed / skills_loaded**/知识命中/上下文用量）——手机上直接回答"skill 用没用上"。

**为什么把这两件事合在一个包**：都是"可观测/可配置"性质的小型 UI 工作，共用一次三端构建与移动端实拍验收，拆开反而增加验收成本。

**怎么验证**：web/mobile 改全局白名单 → config.yaml 正确落盘；写入非法级别被 400 拒绝；mobile 节点展开可见技能字段；三端构建 + 移动端实拍。

## 三、执行顺序与提交节奏

| 顺序 | 内容 | 提交 | 规模 |
|---|---|---|---|
| 1 | 包 A 稳定性加固 | `fix(server)` | 小 |
| 2 | 包 B Phase 0 自指隔离 | `fix(server)` | 小 |
| 3 | 包 B Phase 1 车道键 | `feat(server,web,mobile)` | 中 |
| 4 | 包 B Phase 2 加固+展示 | `feat(server,web,mobile)` | 中 |
| 5 | 包 C 协作可视化 | `feat(server,web,mobile)` | 中 |
| 6 | 包 D 权限/技能 UI | `feat(server,web,mobile)` | 中 |

排序理由：A 和 B0 是正确性问题优先清掉；B1 是用户感知最强的一步；B2 必须在 B1 生效前到位（并行一开，隐患立刻被放大）；C、D 相互独立，放最后。全部工作在 `dev` 分支进行；涉及 server 核心的改动跑全量测试，涉及界面的改动跑三端构建+移动端实拍留证（`logs/gui-shots/`）。

## 四、本轮明确不做（及理由）

- **Phase 3 同工作区并行**（同一项目内 2-3 个任务同时跑）：需要收尾互斥锁+变更集同步替代全量覆盖，是新语义、高风险；不同工作区并行已覆盖大部分提速收益。等 Phase 0-2 稳定后另排。
- **8855 端口多实例 crash loop 治理**（单日 59 次 EADDRINUSE）：属启动器/部署层问题，另行处理。
- **mobile 会话回放/日志查看器**：web 已有，mobile 补齐价值低，暂缓。

## 五、预期效果

- **速度**：不同工作区任务从排队串行 → 立即并行，吞吐上限取决于模型池（当前约 20+ 槽位，公平分配后多任务均分）。
- **成功率**：规划链路对脏数据免疫 + 前置缺失治理（环境预检）双管齐下，50% 的基线应有实质回升。
- **透明度**：模型切换、agent 留言/交接、技能拉取、命令审批全部在双端界面可见；全局配置告别手改 yaml。
