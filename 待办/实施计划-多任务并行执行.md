# 实施计划：多任务并行执行（车道键改造 + 并行加固 + 同工作区收尾互斥）

> 2026-09-15 制定。来源：串行执行问题探讨 + 三路代码调查（taskQueue 车道根因 / 并行资源冲突面 / 双端订阅方式）。
> 状态：**待启动**（未排期）。四阶段独立交付、独立提交，Phase 0/1 零语义风险可先行。
> 配套发现：**自指任务隔离首次执行失效 P0 bug**（见 §1.3 / Phase 0）——独立于并行改造本身，建议无论如何优先修。

---

## 一、背景与调查结论

### 1.1 串行根因在队列层，不在执行层

- `server/src/taskQueue.ts` 车道单槽位：`Lane.running: string | null`（taskQueue.ts:32）+ `tryStart` 守卫 `if (lane.running || lane.blocked) return`（taskQueue.ts:116）——一个车道同一时间只跑一个任务。
- 车道键 `projectId || 'default'`（taskQueue.ts:79）——**所有未绑 project_id 的任务挤同一个 default 车道串行，哪怕工作区完全不同**（纯损失：车道键只看项目不看工作区）。
- 已并行的两层：
  - 任务内节点 DAG 并发——`runGraph` 连续调度器，`maxWorkers = pool.totalAvailable()` 信号量（orchestrator.ts:1413）；
  - 跨 project_id 车道并发（taskQueue.test.ts 已锁定 "different projects run concurrently"）。
- 启动日志自述有意设计：index.ts:256 "one running task per project"。串行背后的真实工程约束是同项目共享同一 git 工作区，任务收尾要回写+验收，并行回写会互相踩踏。

### 1.2 同工作区并行的三个真实冲突（都集中在收尾阶段）

| 冲突 | 位置 | 形态 |
|---|---|---|
| 回写互抹（最严重） | `git.ts:314` `syncToWorkspace` 全量 `cpSync force:true` 覆盖 | 任务 B 的沙箱是启动时拍的快照——A 先回写、B 后收尾，B 用旧快照**全量覆盖抹掉 A 刚回写的成果**。这是快照过期问题，加锁解决不了，必须改同步语义 |
| git HEAD 竞争 | orchestrator.ts:3487-3506 `gitCommit` 切 `coteam/task-*` 分支再恢复 HEAD | 两个任务同时收尾互相切飞 HEAD；`original` 记录的"用户原分支"可能是对方任务分支（workspace.ts:9-10 记载的历史缺陷正是这一形态） |
| 验收互踩 | orchestrator.ts:1049 `runPostMergeAcceptance(workspace)` | 合并后验收测试在同一真实工作区跑，与另一任务的回写拷贝并发 |

另有用户手动操作竞争：API `mergeTaskBranch`（api/index.ts:402）随时可在 workspace 上 checkout/merge。

→ **方案核心：执行阶段（沙箱内，天然隔离）放开并行；收尾阶段（回写/验收/git 提交，分钟级）按 workspace 互斥串行。**

### 1.3 P0 附带 bug：自指任务隔离首次执行失效

`execute()` 内 orchestrator.ts:931 `graph.workspace = execWorkspace`（隔离克隆目录 `<selfdev_root>/<taskId>`），但：

- :938 `createSandbox(workspace)` 用**原始入参**（co-team 主仓库路径）；
- 收尾回写 syncToWorkspace(:1041/:1099)、gitCommit(:1107/:1166)、合并后验收(:1049/:1134) 全部同用原始入参；
- 下游 `recordDeliveryCheck` / `executeCommandAsync` 审批路径用的 `graph.workspace`（重跑时是克隆）与收尾用的原始入参（主仓库）**前后不一致**。

首次执行的自指任务**直接写主仓库工作树**；重跑时 `graph.workspace` 已是克隆路径才走克隆——"主副本零触碰"设计（commit `5697e4f` 引入）未成立。对照引入提交原始代码即如此，非后续回归。

实证吻合：当前工作树遗留改动 `M web/src/composables/useDashboard.ts` 与"自指任务首次执行直接写主仓库"的形态一致。

修复它同时是**多个自指任务可并行的前提**（各自克隆天然互不干扰）。

### 1.4 共享资源压力（并行 ×N 放大）

- **模型池全局槽位**（scheduler.ts:93-105）：单任务 `maxWorkers = totalAvailable()` 可占满全池，并行任务抢槽 → `acquireWithWait` 200ms 轮询/120s 超时（orchestrator.ts:2636-2643）+ 429 端点组避让 60s（scheduler.ts:62-75）+ 健康分冷却连锁——历史两次风暴治理（fc1dd5b/7f15216）的放大面。
- **`executeCommandAsync` stdout/stderr 无界累积**（sandbox.ts:193-209；同步版有 8MB maxBuffer，异步版没有，只在结束时 slice(-4000)）——两次 4GB OOM 治理（ac6a8a0/701aae9）后不能再裸奔。
- **知识库每次 dispatch 双 readAll**（knowledge.ts:151-179 + `recordKnowledgeHits` :224-235 读-改-写逐文件回写），读放大 ×N 且有并行互踩窗口；全局共享 `data/knowledge`。
- 沙箱全量 cpSync ×N（sandbox.ts:75，排除 node_modules/.git 后仍是全量磁盘拷贝）；单一全局日志文件交织（logger.ts:56，有 taskId meta 可辨）。

### 1.5 双端前端现状

- web `ActiveTaskHero.vue:56-74` 只显示 `active[0]`——并行时其余运行任务在工作台不可见；mobile 无单任务假设（按 taskId 列表渲染）。
- 数据层双端已按 taskId+nodeId 键控（useDashboard web/mobile），多任务就绪，无需改造。
- `QueuePanel.vue`（web，:6）与 `TaskListView.vue:323`（mobile）显示单 `running_task_id` 字符串。
- 事件流单 WS 全局广播（api/index.ts:1744-1786，`coteam:dashboard` 单频道），payload 带 task_id 前端分流，机制上无需改；事件速率随并行任务数线性增长（agent_delta 每任务每节点 ≤60 条/分护栏已存在）。

## 二、方案总览（四阶段，按工程量/风险递增）

| 阶段 | 内容 | 效果 | 风险 |
|---|---|---|---|
| Phase 0 | 自指隔离 P0 修复 | 自指任务真正零触碰主副本；多个自指任务可各自并行 | 小改动 |
| Phase 1（L0） | 车道键改按 workspace | **不同工作区任务立即并行**，零新语义 | 零语义风险 |

## Phase 0 — 自指隔离 P0 修复（先行，独立提交）

**改动**：`server/src/orchestrator/orchestrator.ts` execute()——克隆准备后统一本地变量 `workspace = execWorkspace`（:931 前后重赋值），使 :938 createSandbox 及全部收尾回写/验收/gitCommit 的目标均为克隆路径；`emitProgress('execute_start')` 的 workspace 字段同步为克隆路径。

**测试**：新增 selfdev 隔离回归测试（temp 假主仓库 + self_ref 图，断言 createSandbox/syncToWorkspace/gitCommit 收到的目标均为克隆路径；依赖注入/spy 简化）。

---

## Phase 1 — L0 车道键改 workspace（不同工作区立即可并行）

**server/src/taskQueue.ts**：

- `keyFor` 改为按规范化 workspace 生成键（`path.resolve` + 小写 + 正斜杠归一，形如 `ws:<path>`）。
- **项目车道也映射到其 workspace 键**（同项目⇒同工作区⇒同键；避免"绑项目与不绑项目但同工作区"分裂成两个车道绕过串行保护）。Lane 增存 `projectId`/`workspace` 供展示。
- `QueueSnapshot` 增 `workspace` 字段；project_id 语义不变（项目车道返回项目 id，纯工作区车道 null）。
- 车道状态纯内存无持久化（taskQueue.ts:63-64），键形变更无迁移成本；resume/clear 按 key 透传不受影响。

**server/src/index.ts:256**：启动日志文案更新（one running task per workspace）。

**双端 UI**（AGENTS.md 硬性：UI 改动必须双端同步 + 移动端实拍验收）：

- web `QueuePanel.vue` 车道标签支持工作区车道（`工作区队列 <basename>`）；
- mobile `TaskListView.vue:323` 同步；
- 两端 api/index.ts 的 QueueSnapshot 类型补 `workspace` 字段。

**测试**：taskQueue.test.ts 增用例——

1. 不同 workspace、未绑项目 → 并行；
2. 同 workspace（含绑/不绑项目混用）→ 同车道串行；
3. 既有跨项目并行用例保持绿（语义从"按项目"变为"按项目的工作区"，同项目必同工作区，兼容）。

**效果**：无需任何并发配置，不同工作区任务立即并行；同工作区维持现状串行（安全）。

## Phase 2 — L1 并行加固（并行不炸）

1. **stdout 封顶**：sandbox.ts `executeCommandAsync` stdout/stderr 滚动截尾（各保留尾部 1MB），消除隐性 OOM 源。
2. **知识库缓存 + 互斥**：knowledge.ts readAll 按 mtime 缓存文件内容（进程内，mtime 失效）；`recordKnowledgeHits` 读-改-写加进程内互斥（按知识库目录键）——消除读放大与并行互踩。
3. **模型池公平分配**：taskQueue 暴露 `activeTaskCount()`；index.ts 注入 orchestrator 回调；runGraph 的 `maxWorkers = max(1, floor(totalAvailable / activeTaskCount))`（activeCount≥2 时生效，单任务行为不变）。车道启动容量闸 `usableCapacity()>0` 保持。
4. **前端多活跃展示（双端）**：web `ActiveTaskHero.vue` 显示 hero（最高优先级）+ "另有 N 个任务并行中"徽标（点击进任务中心）；mobile TaskListView 队列区同步多车道展示；**验收含移动端实拍（8857）**。

**测试**：stdout 封顶单测；knowledge 缓存失效与并发回写单测；maxWorkers 公平分配单测（activeTaskCount mock）。

## Phase 3 — L2 同工作区并行（收尾互斥 + 变更集同步）

1. **多槽位车道**：
   - `Lane.running: string | null` → `running: string[]`；
   - 新增 `orchestrator.lane_concurrency` 配置（config.ts 解析，**缺省 1 = 现状不变**，显式调 2 才开同工作区并行）；
   - tryStart 改 while 填充至并发上限；onFinished 从数组移除（waiting_approval 释放槽位逻辑对应调整）；enqueue 重入检查改 `includes`；
   - `QueueSnapshot` 增 `running_task_ids`（保留 running_task_id=首个以兼容）。
2. **收尾互斥锁**：orchestrator 内 per-workspace 异步互斥（`Map<string, Promise>` 链式锁），包裹整个收尾块（finalizing → syncToWorkspace → post-merge 验收 → gitCommit）。执行并行、收尾分钟级串行；锁等待期间任务保持 finalizing 状态可见。
3. **变更集同步替代全量覆盖**：
   - git.ts 新增 `syncChangeset(sandbox, workspace, baseSha)`——execute 在 ensureBase 后捕获 baseSha；
   - 收尾用 `git diff --name-status baseSha..HEAD` 得变更清单，逐文件判定：目标工作区文件与 base 内容一致（期间未被他人改动）才覆盖，不一致即冲突→跳过并记录；删除同理；
   - 冲突 → 任务以明确错误收场并保留沙箱（沿用现有恢复哲学），**绝不静默互抹**；
   - 非 branch_workflow 路径（mergeChanges mtime 比对）不动。
4. **双端 UI**：QueuePanel/TaskListView 显示多执行中任务（A、B）；hero 徽标沿用 Phase 2。

**测试**：lane_concurrency=2 并行/人工门放行/失败阻塞语义用例；syncChangeset 单测（两个临时仓库模拟 A 先回写、B 后收尾的冲突与无冲突两路）；收尾互斥顺序用例；全量 server 测试 + 三端构建 + 双端实拍。

## 三、提交与验收节奏

- 每阶段独立 commit（中文 conventional）：Phase 0 `fix(server)`、Phase 1/2/3 `feat(server,web,mobile)`。
- 每阶段跑 server 全量测试 + web/mobile 构建；UI 阶段（1/2/3）含 8857 双端实拍截图留证（logs/gui-shots/）。
- 交付顺序即风险递增；Phase 3 缺省关闭，配置级回退。

## 四、风险与回退

- **最大外部风险**：免费模型池 429 风暴放大——公平分配 + 既有端点组避让/冷却兜底；若仍抖，`lane_concurrency` 回 1 即回现状。
- 车道键形变更无持久化状态，重启自动重建，无回退成本。
- `syncChangeset` 是唯一"新语义"点：行为从"静默覆盖"变"显式报冲突"，需在提交信息与开发路线写明。

## 五、并行安全、无需改动的部分（调查确认）

- bus KV 全部按 `task:<id>:*` 命名空间隔离（bus.ts 键设计）；
- askGate / activeAgents / taskTokens / progress 节流均按 taskId 键控；
- LLM SDK client 按 `base_url|api_key` 缓存共享且每请求无状态（llm.ts:72/119-132）；
- 事件 payload 带 task_id，前端分流（web/mobile utils/events + useDashboard）；
- web/mobile tasks/nodeRuntime/deltas 数据结构均已按 taskId+nodeId 键控；
- 自指任务克隆按 taskId 隔离（Phase 0 修复后）。
