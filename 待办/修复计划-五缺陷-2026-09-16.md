# 修复计划：任务跟踪实录确认的 5 项系统缺陷

> 2026-09-16 制定。来源：英语学习任务（o3xmkraj）全程跟踪实录（开发路线.md 同日章节）。
> 基线：dev 分支最新（含 MCP 集成 c711df3/48a67cb 与跟踪期修复 5c292fe/0a10b53/90dc8cf）。
> 全部为 server 侧修复 + 两端事件文案；无数据库/配置结构变更。

## 缺陷 1（P1）：phantom 完成无守卫——账面 completed、产物不存在

**解决什么问题**：429 限流风暴下，agent 抢不到写窗口却"幻觉完成"——changes 申报了一堆文件、实际沙箱里不存在（s3-4 两次复现：AiClient 声称实现、分支里无 lib/services/ai_client.dart）。下游节点按申报等文件 → precondition blocker，任务卡人工门。现有 `recordDeliveryCheck`（orchestrator.ts:1839-1877，"fake completion" detector）**已经计算出 phantom 列表，但结果只写 result.delivery_check + 日志警告，不影响节点状态**（全仓库仅 3 处消费：写结果/日志/metrics）。

**做什么**
1. `recordDeliveryCheck` 返回检查结果（现为 void）。
2. 两个调用点（orchestrator.ts:2156 正常成功、:2216 接管成功）在 `finalizeNodeSuccess` 前做分级裁决：
   - **全 phantom**（申报 changes 全部不存在，且 git 实际变更为空）：节点判 `failed`，`error_type='content'`，error 写明"N 个申报文件均未落盘（假完成）——模型在限流/中断下未真正写盘"，走既有失败处理（可换模重试/人工门）；
   - **部分 phantom**：从 `result.changes` 剔除不存在的条目（下游不再等不存在的文件——s2-2/s3-5 的 precondition 失败正是这么来的），journal 保留完整审计记录；
   - orchestrator 合并节点（无文件产出语义）跳过强校验。
3. 新事件 `node_phantom_detected`（附 phantom 清单），两端 events.ts 中文文案（"节点申报的 N 个文件未落盘——已拦截假完成"）。

**怎么做**：改动集中在 orchestrator.ts（recordDeliveryCheck 签名 + 2 调用点）+ 两端 utils/events.ts 文案。phantom 判定复用现有 normalizeReportedPath/reportedPaths/存在性检查（1687-1698、1854-1860），不新造轮子。

**为什么**：已有 detector 只差"最后一公里"——把计算结果接入状态机。相比新造校验器，复用既有对账逻辑改动最小、口径一致。

**验证**：单测——mock dispatch 返回 success + changes ['a.txt: ok']，沙箱无 a.txt → 节点 failed；changes 部分存在 → 剔除缺失项且 completed；两端构建 + 事件文案渲染。

## 缺陷 2（P1）：监督者陈旧错误催办循环——单节点累积 15 条噪声

**解决什么问题**：节点重置后旧错误文本让监督者每 10 分钟心跳注入一次催办（s2-4 开局注入 15 条，稀释模型注意力）。根因有二：① `execute()` 重置节点时**只改 status 不清 error/error_type**（orchestrator.ts:977-980 对比 retry 端点的清理逻辑）——监督者 buildDigest 读节点行 `status 错误:...`（supervisor.ts:307-326）看到陈旧错误；② nudge 走 interventions 队列无内容级去重（supervisor.ts:224-235 → pushIntervention），同文可无限累积。

**做什么**
1. `execute()` 重置循环补 `n.error=''`、`(n as any).error_type=undefined`、`n.needs_human=false`（对齐 retry 端点的清理语义）——根因修复，一行级。
2. `runAction` case 'nudge'（supervisor.ts:224-235）push 前查 `task:intervene:{taskId}` 队列：存在同文本未消费项则跳过（队列为消息数组，直接 includes 比对文本）。

**为什么**：① 治本（监督者读的字段从此干净）；② 治标兜底（正常长任务中监督者对同一卡点重复催办同样有害，队列去重代价 O(n)、队列上限 50）。

**验证**：单测——execute 重置后节点 error 为空；同文 nudge 两次队列只有一条。

## 缺陷 3（P1）：E25 上游合并冲突静默跳过——下游 precondition blocker

**解决什么问题**：并行兄弟分支合并冲突时 `merge --abort` 后 "node continues with what merged"（orchestrator.ts:2015-2019 只 warn），冲突分支的独有文件对下游不可见（s3-5 实证：s3-4 的 ai_client.dart 缺失 → 验收节点 blocker）。

**做什么**：`git.ts` 的 mergeIntoCurrent/mergeAllNodes 冲突处理从"abort + 记 conflicts"改为**冲突以上游分支版本续合**：
1. `git merge --no-commit --no-ff <branch>` 冲突时，不 abort：读 `git status --porcelain` 的冲突条目（UU/AA/AU/UA/DD），对每个冲突文件 `git checkout <branch> -- <file>`（取上游版本），`git add -A` 后照常 commit；
2. `conflicts` 仍如实上报（记文件清单）；
3. orchestrator.ts:2017 的 warn 升级为 journal 条目 + `branch_converge_conflict` 事件（附文件清单），两端 events.ts 文案（"上游分支 X 合并冲突 N 文件，已以上游版本并入"）。

**为什么**：E25 场景里节点分支**刚从 parent 切出、本节点尚无自有改动**——冲突文件取上游任意一方都严格优于"缺失"；上报保留审计。语义变化点（abort→theirs 续合）在 git.ts 注释与提交信息明示。

**验证**：git.ts 单测——两兄弟分支改同一文件不同内容 → mergeIntoCurrent 不抛、目标文件=上游版本、merged/conflicts 记录正确；既有 E25 用例保持绿。

## 缺陷 4（P2）+ 5（P2）：流内可控性——节点预算墙钟 + 取消打断流

**解决什么问题**：① 节点级预算（agent.yaml timeout，语义即"总时长预算超线转人工"）只在轮循环边界检查（orchestrator.ts:3126-3134），单轮慢滴流可挂 30-50 分钟（wallclock_cap=0 时墙钟保险丝全关，llm.ts:173-176）；② 取消只写 bus flag 轮询，卡死的 LLM 流无法打断（llm.ts 的 externalSignal 分支是死代码——dispatch 传 undefined）。

**做什么**
1. **预算墙钟**：dispatch 的轮循环已有 node deadline 计算（3126-3134），把"剩余毫秒数"作为 chat 第 6 参 `wallclockCapMs` 传入每轮调用（orchestrator.ts:3139/3185/3297 三处）；到线 watchdog abort 抛 `wallclock_cap(...)`——dispatch catch 识别该错误且 deadline 确已到线 → 打 `[node-budget]` 前缀停止模型阶梯（走既有 env-defect/budget 停阶梯语义，orchestrator.ts:111-116），而非当作模型错误换模空转。
2. **取消打断**：orchestrator 增加 `taskSignals = new Map<taskId, AbortController>()`；execute() 开头创建、finally 清理；dispatch 三处 chat 调用传入 `signal: controller.signal`；新增 `abortTask(taskId)` 供 `POST /api/tasks/:id/cancel`（api/index.ts:387-395）调用——abort 使 in-flight 流立即中断（llm.ts:262/270 已有"LLM 调用被外部取消"语义），轮循环既有 isCancelled 检查接管收尾。
3. 范围裁剪：executeCommandAsync 的 signal 传入（tools/acceptance 多处）列为后续——命令有 timeoutSec 兜底，本轮聚焦 LLM 流。

**为什么**：① 把 timeout 的文档语义真正落到流内（复用现成 watchdog 与 per-call 参数，llm.ts 零新机制）；② 复用 llm.ts 现成 externalSignal 消费分支（262/270），只补"谁传 signal"与"谁 abort"。两者共同消灭"单节点无上界挂死"这一跟踪实录中最耗时的故障形态。

**验证**：llm 层单测（仿 streamFlood.test 的 fake 流）——capMs 到线抛 wallclock_cap；externalSignal abort 抛取消错误。orchestrator 层单测——dispatch 挂起时 abortTask 使 mock chat 收到 aborted signal；mock 慢流 + 小节点预算 → 节点 error 带 [node-budget]。

## 执行顺序与提交切分

| 序 | 提交 | 内容 | 规模 |
|---|---|---|---|
| 1 | `fix(server)` | 缺陷 2：execute 重置清 error + nudge 去重 | 小 |
| 2 | `fix(server,web,mobile)` | 缺陷 1：phantom 完成守卫 + 事件双端文案 | 中 |
| 3 | `fix(git,server,web,mobile)` | 缺陷 3：E25 冲突以上游版本续合 + 事件双端文案 | 中 |
| 4 | `feat(server)` | 缺陷 4+5：流内节点预算墙钟 + 取消打断流 | 中 |

顺序理由：1 最小且根因级；2 是当前人工门的直接根因；3 依赖 2 的干净基线验证；4 复杂度最高放最后。

## 全局验收

- server 全量 vitest **单 worker**（`--maxWorkers=1`——并行模式下 git 重型测试有资源竞争假失败，跟踪实录已实证）；tsc 三端构建。
- UI 改动仅事件文案（两端 utils/events.ts），按 AGENTS.md 做双端构建 + 移动端事件流实拍（8857 vite dev 或 8855/m）。
- 完成后开发路线.md 追加章节；任务 o3xmkraj 用修复版续跑 s3-4/s3-5/merge-s3 收尾（phantom 守卫会拦住幻觉完成）。

## 明确不做

- executeCommandAsync 的 signal 贯通（命令有 timeoutSec 兜底，后续单独做）。
- 重启中断计数区分诊断性重启（观察项，暂无可靠判据）。
- 流内打断命令执行（同 1）。
