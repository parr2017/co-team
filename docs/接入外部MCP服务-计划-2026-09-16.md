# 任务计划：接入外部 MCP 服务（2026-09-16）

> 状态标记：⬜ 未开始 / 🔄 进行中 / ✅ 完成（执行时完成一步勾一步，禁止提前勾选）

## 人话摘要

- **解决什么问题**：co-team 的 Agent 只能调用内置工具（读文件/跑命令/截图等），接不了外部工具生态——GitHub、文件系统、浏览器自动化这类现成 MCP 服务的能力。
- **做什么**：给系统加一个"MCP 客户端"，连接外部 MCP server，把它的工具以 `mcp__<服务名>__<工具名>` 暴露给 Agent（任务管线和群聊都能用）；再做一套配置 UI（web 管理、mobile 只读状态）。
- **怎么做**：后端用官方 SDK（`@modelcontextprotocol/sdk`）做客户端，新增 `server/src/mcp/` 管连接与转发，config.yaml 存配置 + 新增管理 API（含测试连接）；web 在现有设置对话框加「MCP服务」tab，编辑框=基础表单+可折叠高级 JSON；agent 编辑框勾选可见服务；再往工具分发器与两处教学提示里接入。
- **做完后效果**：在界面上点几下就能接入外部工具服务、当场测试连不连得上、勾选给你的 Agent；连不上只降级不影响主流程；不配置不勾选时行为与现在完全一致。

## 1. 背景与目标

问题从哪来：co-team 工具面封闭，缺乏对接外部 MCP 工具生态（stdio 本地进程 / Streamable HTTP 远程）的能力。用户要：MCP client 接入 + 不做成手改 yaml 的配置 UI（含测试连接、可连接状态、高级设置用 JSON），web 管理 + mobile 只读状态一致。

成功标准（可验收）：
1. UI 能新增/编辑/删除 MCP server 并测试连接（不落盘探测，成功显示工具数，失败显示具体报错）。
2. 服务状态灯实时显示「可连接 / 不可连接 / 禁用」。
3. 编辑框基础表单 + 高级设置 JSON 都能保存并热生效（不用重启）。
4. Agent 编辑框可勾选「绑定 MCP 服务」，勾选后任务与群聊都能真实调用外部工具并拿到结果。
5. mobile 显示服务连接状态（双端一致）。
6. 任一 server 连接失败只降级（软错误）不炸主链路；未配置/未勾选时行为与现在完全一致。

## 3. 方案与取舍

| 方案 | 做法 | 优点 | 代价/风险 |
|---|---|---|---|
| A（推荐）桥注入 | tools.ts 只依赖 `McpBridge` 接口，orchestrator/discussion 注入 `McpManager` 实现，缺桥软错误 | 与 askBridge/vision 同构、架构最一致、测试易 mock | 多一层接口；无 |
| B 全局单例直调 | tools.ts 直接 import McpManager | 少一层 | 强耦合、测试难、违背现有模式 |
| A（推荐）官方 SDK | 不自写 JSON-RPC，用 `@modelcontextprotocol/sdk` Client + stdio/Streamable HTTP transport + InMemoryTransport 测试桩 | 协议成熟、测试桩现成 | 新增依赖（仅 server 工作区） |
| C 自写协议 | 手写 MCP JSON-RPC client | 无依赖 | 大坑，否决 |
| A（推荐）UI 保存即热生效 | PUT 写回 config.yaml + `McpManager.applyConfig` 差异热连/断连 | 不用重启，仿 saveModelPool | diff 写错会误连误断（有校验兜底） |
| A（推荐）基础表单+高级 JSON | 表单管 name/type/enabled/command/url；其余字段进可折叠 JSON 文本域，格式化+校验后才能保存 | 常用字段友好、任意扩展字段可透传 | JSON 校验需双保险（前端+后端） |
| A（推荐）agent.yaml 白名单+UI 多选 | agent.yaml 加 `mcp_servers`，Agent 编辑框多选写回 | 安全默认关闭、可视化、对齐绑定技能交互 | agent.yaml 双通道写入需一致 |

推荐 A 方案组合，理由：全部复用现有桥/写回/面板模式，架构一致且每步可独立验证；JSON 透传满足任意 MCP server 的扩展字段需求，同时基础表单保证常用操作低门槛。
