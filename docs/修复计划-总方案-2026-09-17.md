## 三、方案与取舍

### B1 验收软门：配置化策略，而非启发式解析测试输出

| 方案 | 做法 | 优点 | 代价/风险 |
|---|---|---|---|
| **A（选定）** | 任务级 `acceptance_policy: strict/tolerant`（默认 tolerant）；tolerant 下验收失败 → `completed_with_warnings` | 语义明确可控；不改测试输出解析；用户可按项目选择 | 需加一个 TaskStatus 值 + 双端状态映射 |
| B（否） | 解析测试输出分"编译失败/断言失败"定 severity | 无新配置 | npm/pytest 输出格式漂移会导致误判，脆弱 |
| C（否） | 全局去掉硬门 | 改动最小 | strict 用户失去强约束，验收形同虚设 |

选 A 理由：判定权交给用户而非脆弱的文本解析；默认 tolerant 直接回应"成功率 50% 最大杀手"——多数项目测试套件不完整或含 flaky 用例，一刀切判死不公平；strict 保留给测试基建完善的项目。

### B10 编排锁：实例抢锁，非主实例跳过 sweep

| 方案 | 做法 | 优点 | 代价/风险 |
|---|---|---|---|
| **A（选定）** | bus 锁 `orchestrator:leader`（bootId + pid，TTL 30s，启动续期）；抢到锁才跑 sweep | 改动集中（index.ts 启动段 + 一个锁 helper）；dev watch 抢不到锁天然跳过 | 锁过期窗口内两实例都非 leader → 都跳过 sweep（可接受：漏 sweep 会被下个正式重启补上，误杀不可逆） |
| B（否） | 任务图加 owner_pid + 心跳字段 | 粒度细到任务 | 改 TaskGraph 结构 + dispatch 循环加心跳刷新，影响面大 |

选 A 理由：sweep 是全局动作，全局锁语义正好匹配；任务级心跳是过度设计。路线图 E16 修复方向（"实例启动时抢占编排锁，非主实例跳过 sweep"）与本方案一致。

### B2 错误可操作：前端关键词映射 + 统一 showError helper

服务端错误已有中文 detail（HttpError message），本轮**不动服务端错误结构**（避免三端 API 契约大改），前端按 detail 关键词匹配到操作建议：

| 关键词 | 操作建议 |
|---|---|
| 验收/acceptance | "查看验收报告 → 任务详情·验收面板；可在执行策略中切换验收模式后重跑" |
| 模型/model/pool | "打开设置 → 模型池查看各模型健康分；或对任务手动换主模型" |
| 不存在/404/not found | "任务可能已被删除，刷新任务中心确认" |
| Token/token/401 | 保留现有完整引导（已达标） |
| 其余 | 原样展示 detail，不编造建议 |

`request()` throw 的 Error 挂 `hint` 属性，新增 `showApiError(e)` helper（web/src/utils/），组件逐步替换 `ElMessage.error(e.message)` → `showApiError(e)`（本轮替换高频 10 处，其余渐进）。

### B6 模型切换原因：payload 补 from/to/reason

reason 由调用点上下文推导（有 `lastErr`）：连接类错误 → `连接失败`；429/503 → `限流`；其余 → `执行失败`。不改事件类型，双端只改文案模板。scheduler 层不加改动（原因在 orchestrator 调用点可得，下沉到 scheduler 反而要改返回签名）。

### B3 路由：4 个 tab 先路由化，任务深链后续

`/`、`/tasks`、`/project`、`/discuss` 四路由 + `createWebHashHistory`（无需服务端 rewrite 配置，file:// 与现有部署方式都兼容）。任务详情是 dialog 非页面，`/task/:id` 深链涉及 dialog 状态提升，**本轮不做**（决策点 2）。

### B5 审批收件箱：web 对齐 mobile 的聚合逻辑

复用 mobile `ApprovalsView.vue` 的数据聚合口径（从任务列表拉 5 类待办），web 新建 `/approvals` 页 + 导航 tab 徽标。**放在批次三**因为它需要 B3 的路由先就位。

### 批次划分逻辑

批次一全部是 server 端正确性且共享 orchestrator.ts 改动面（假完成计划步骤 4/5/6 与 B10 同文件），一起做一次全量回归；批次二引入新状态与事件语义（B1 改 TaskStatus，B6 改事件 payload），需要双端同步；批次三是 web 架构升级（B3 依赖少但改动面大，B5 依赖 B3）。批次间无循环依赖，可按序独立交付。

**步骤 12：B10 编排锁——非主实例跳过 sweep**

- **做什么**：新增 server/src/leaderLock.ts（≈40 行）：`acquireLeaderLock()` 用 bus setIfAbsent 写 `orchestrator:leader = {bootId, pid, at}`（TTL 30s，setInterval 10s 续期，进程退出释放）；`isLeader()` 读锁比对 bootId。
- **改哪**：`server/src/index.ts:234-237` 启动段——先 `acquireLeaderLock()`，仅 `isLeader()` 为真时执行 `sweepInterruptedTasks()`，否则日志"非主实例（已有 leader pid=X），跳过启动清扫"。
- **为什么**：dev watch 热重载重启进程必触发 sweep（index.ts:234），无属主校验会把另一实例正在执行的任务标 interrupted（orchestrator.ts:381-436 现状无任何检查）。锁方案让"谁能 sweep"由先到者决定，watch 实例后启动天然抢不到。
- **怎么验证**：新单测 leaderLock.test.ts——两实例先后 acquire，后者 isLeader=false；TTL 过期后可重新抢占。手测：起正式 server 后再起 tsx watch 实例，watch 启动日志出现"跳过启动清扫"，正式实例运行中任务状态不变。
- **状态**：⬜

**步骤 13：B9 config 启动校验 + 回退显式化**

- **做什么**：`server/src/config.ts:223` 读 permissions 后立即校验 `level`：非法值 → `logger.warn` 明确写出"permissions.level 'X' 非法（合法值：五档列表），已忽略，实际生效由 policyFromConfig 决定（有白名单 → whitelist_auto，否则 approve_required）"，并把 level 置空让回退路径唯一。`server/src/sandbox.ts:35` 回退后补一条 info 日志打出最终生效级别。
- **为什么**：现状非法值只 warn 一次正则文案（sandbox.ts:30-32），回退后用户不知道实际生效的是什么；config.ts 层校验把问题拦截在配置加载时（最早、最可见），与 API 端点的 400 校验形成两道防线。

- **怎么验证**：单测——mock 验收 returncode 1 + policy 缺省 → 任务 completed_with_warnings；policy=strict → failed（既有用例保持绿）；notify 触发 task 完成事件。双端状态映射见步骤 16。
