# 飞书长连接接入计划（v1）— 2026-09-26

## 人话摘要

**解决什么问题**：co-team 已有一套飞书机器人（发任务卡片、@机器人建任务），但入站消息走 HTTP 回调，要求服务器有公网地址——无公网 IP 且不做内网穿透的部署形态下，这套双向能力用不起来，现在只剩单向的群机器人 webhook 推文本（`COTEAM_FEISHU_WEBHOOK`）。

**做什么**：给飞书接入加第二条入站通道——飞书官方"长连接"模式（服务器主动连飞书的 WebSocket，不需要公网 IP/域名/证书），并把审批停靠通知升级成可点击的交互卡片。

**怎么做**：新增一个长连接网关模块（飞书官方 Node SDK 的 WSClient），复用现有 `webhook.ts` 里已写好的事件处理逻辑；新增审批卡片构建与回调处理；补两条查询指令。执行引擎（orchestrator/taskQueue）零改动。

**做完后效果**：手机飞书群里——任务状态卡片实时原地更新、审批停靠时点卡片按钮直接恢复/取消任务、@机器人发文本建任务、发指令查在跑什么。全程零公网暴露（仅出站 443）。

### 目标（v1 验收标准）

1. 无公网 IP、无穿透形态下，飞书群内完成闭环：
   - @机器人文本建任务（复用 `processEvent`）；
   - 审批停靠（approval_required / command_pending_approval / queue_human_gate）推交互卡片，点「批准 / 取消」任务实际恢复或取消，卡片原地更新为结果；
   - `/tasks` `/queue` 查询指令返回实时状态；
   - 任务生命周期卡片照常原地更新（现有行为不回退）。
2. 服务器零公网暴露。

## 2. 现状与约束

- **不改执行引擎**：orchestrator.ts / taskQueue.ts / notify.ts 一律不动；审批回调只是复刻既有 API 端点的副作用（Redis 写 + enqueue），这些端点本身继续服务 mobile/web。
- **HTTP webhook 通道保留**：与长连接共存，靠 `seenEvent` 共享去重防双处理；已有部署零破坏。
- **卡片格式红线**：审批按钮必须用新版卡片 JSON 2.0（`schema: "2.0"` + behaviors），否则 `card.action.trigger` 在长连接下收不到；旧版任务状态卡片不含按钮，保持 1.0 不动。
- **回调 3 秒响应约束**：卡片回调里只做校验 + Redis 写 + enqueue（毫秒级）+ 异步 updateCard，绝不等待节点续跑结果。
- **平台事实（假设，待 Step 3 联调验证）**：长连接模式下事件为明文推送，无需 encrypt_key/verification_token；卡片回调事件体的具体字段以 SDK `cardActionHandler` 实测为准。

---

## 3. 方案与取舍

**方案 A（推荐）：官方 SDK WSClient 网关 + 复用 processEvent**
- 新增 `server/src/feishu/wsGateway.ts`：`WSClient` + `EventDispatcher`，把 `im.message.receive_v1` 转交现有 `processEvent()`（先过 `seenEvent` 去重），`card.action.trigger` 转交新增审批回调处理器。
- 优点：长连接握手/心跳/断线重连全部由官方 SDK 承担；建任务/指令/去重逻辑零重写。
- 代价：新增依赖 `@larksuiteoapi/node-sdk`（仓库代码已用 `AbortSignal.timeout` 等 Node 18 特性，SDK 要求 Node ≥16，兼容）。

**方案 B（否决）：不用 SDK 手写 WS 协议** — 长连接协议有专有帧格式与签名，无完整公开文档，手写脆弱且不在官方支持范围。

**方案 C（否决）：审批按钮走旧版卡片回传** — 旧版回传必须 HTTP webhook URL，长连接不支持，与无公网约束物理冲突。

**出站发送不动**：`messageService.ts`（手写 fetch + 429 退避）继续使用，不为发消息引入 SDK Client——替换是纯风险无收益。

## 5. 步骤分解

### Step 0（人工前置）：创建飞书应用
- **做什么**：[开放平台](https://open.feishu.cn)创建企业自建应用，记录 App ID/Secret；事件订阅方式选「使用长连接接收事件」；订阅 `im.message.receive_v1`；开通 im:message 相关权限并**发布版本**。
- **为什么**：长连接仅支持企业自建应用，且未发布的应用收不到事件（GitHub 上长连接失败案例的常见根因）。
- **验证**：后台显示长连接模式 + 版本已发布。

### Step 1：依赖与配置
- **做什么**：`server/package.json` 加 SDK；`config.ts` 的 `FeishuConfig` 加 `ws_enabled?: boolean`（缺省 false，显式开启）、`approvers?: string[]`（open_id 白名单）；`config.example.yaml` 补注释。
- **为什么**：行为开关显式化，升级不突变；审批权限收敛到配置。
- **验证**：`npm install` + `npm run build` 通过；单测断言新字段读取与缺省值。

### Step 2：审批卡片模块 `approvalCards.ts`
- **做什么**：
  1. 订阅 NOTIFY 频道，过滤 `approval_required` / `command_pending_approval` / `queue_human_gate`，发送 2.0 格式审批卡片（按钮 `action_value` 携带 task_id / node_id / command_id / action）；
  2. 回调处理：批准 → 复刻 `api/index.ts:778-790` 副作用（名单写入 + enqueue）；取消 → 复刻 `:460-469`；命令拒绝 → `resolvePendingCommand(taskId, commandId, false)`；命令批准 → `resolvePendingCommand(..., true)`。为避免复制粘贴，把上述端点核心逻辑抽成共享函数（放在 feishu 模块内、由 api 挂载处注入 deps，与现有 `FeishuDeps` 风格一致）；
  3. `approvers` 白名单校验（未配置白名单 → 卡片不渲染按钮，只显示信息）；
  4. journal 审计：谁（open_id）、何时、批了什么，写任务 journal；
  5. 卡片原地更新为「已批准/已取消 · 操作人」，过期点击回「任务已结束」卡片。
- **为什么**：推送侧事件全部现成，只缺"按钮 + 落地动作"；审计补上"谁批的"（现 dashboard token 无身份概念，飞书侧反而增强）。
- **验证**：单测——mock 回调 JSON，断言名单写入/enqueue 调用/白名单拒绝/幂等重复点击/过期卡片五条路径。

### Step 3：长连接网关 `wsGateway.ts`
- **做什么**：`WSClient({appId, appSecret}).start({ eventDispatcher, cardActionHandler })`；`im.message.receive_v1` → `seenEvent()` 去重 → 复用 `processEvent(body)`；`card.action.trigger` → Step 2 处理器；进程优雅退出时 `stop()`。挂载在 `api/index.ts` 注册流程内（与 webhook 同处拿 ctx），`ws_enabled` 才启动。
- **为什么**：网关只是"运输层"，业务全在既有模块里，改动最小。
- **验证**：配置测试应用凭据本地起服务 → 日志出现长连接建立成功；飞书群 @机器人发文本 → 任务创建并回卡片；点审批按钮 → 任务恢复。**联调中确认卡片回调事件体字段（假设项）。**

### Step 4：查询指令 `/tasks` `/queue`
- **做什么**：`commands.ts` 扩展两条指令：`/tasks` 当前项目最近任务与状态、`/queue` 车道快照；`CommandDeps` 加 `listTasks/listQueue`，数据源复用 `/api/tasks`（:1063）与 `/api/queues`（:533）的底层查询。
- **为什么**：查询是聊天形态覆盖 H5 的最高频替代动作；commands.ts 纯函数模式已验证易测。
- **验证**：单测（纯函数，mock deps）+ 群内实测输出格式。

### Step 5：回归 + 文档
- **做什么**：全量测试 + 三端构建（AGENTS.md：核心文件改动需全量测试与构建）；`docs/feishu_architecture.md` 补长连接章节（两种入站通道对比、配置项、开关）。
- **验证**：`npm test` 全绿、三端构建通过；按验收标准清单手工过一遍（建任务/审批批准/审批取消/命令拒绝/查询/生命周期卡片更新）。

### Step 6：配置可用性保障（轻量，用户确认只要"能配置"即可）
- **做什么**：不做完整向导页，把配置体验做实三件事——① `config.example.yaml` 的 feishu 段注释给出一步步的后台操作路径（点哪里、选哪个模式、订阅哪个事件）；② 启动与连接过程日志明确成功/失败原因（凭据缺失/长连接断开/白名单条数）；③ `/status` 指令显示网关连接状态与审批白名单配置状态。
- **为什么**：无公网部署下 HTTP webhook 永远不通，用户最容易困惑"为什么没反应"——日志与状态可自查是最低成本的可观测性。
- **验证**：故意配错 app_secret 启动 → 日志给出可定位的错误；`/status` 回复包含网关状态。

## 6. 风险与回滚

| 风险 | 缓解 | 回滚 |
|---|---|---|
| SDK 与 Node/TS 编译配置冲突 | Step 1 先装先编译，不通过即止步 | `npm remove`，无残留 |
| 卡片 2.0 字段写错 / 飞书文档变动 | Step 3 先发最简两按钮卡验证回调通路，再丰富样式 | 回退纯文本通知（即现状） |
| 回调处理异常导致飞书重推风暴 | `seenEvent` 去重共用；回调 handler 全 catch，失败回错误卡片 | `ws_enabled=false` 关闭网关 |
| 无关成员点审批按钮 | `approvers` 白名单 + 未配置则不给按钮 + journal 审计 | 收紧白名单 |
| HTTP webhook 与 WS 双通道双处理 | 共用 `seenEvent` 去重；文档明确二选一推荐 | 关掉任一通道 |
| 白名单 open_id 配错导致无人能批 | 启动日志打印已加载白名单条数；`/status` 指令显示审批配置状态 | 修正配置 |

**总回滚开关**：`config.feishu.ws_enabled = false` → 行为完全回到现状。

## 7. 决策点（已确认：2026-09-26 用户拍板按默认执行）

1. **节点级审批「取消」按钮语义** = 取消整个任务（现 API 无节点级拒绝路径）。✅ 按默认：批准/取消两按钮。
2. **`approvers` 白名单缺省策略**：未配置时审批卡片不渲染按钮（安全优先），建任务等非审批能力不受限（沿用现状语义）。✅ 按默认。
3. **`ws_enabled` 缺省值**：false，显式开启。✅ 按默认（升级不突变）。
4. **HTTP webhook 是否保留**：保留现状挂载逻辑不动，无公网时它自然不工作。✅ 按默认：保留。
5. **接入向导**（2026-09-26 补充讨论）：不做完整向导页，按"只要能配置就行"降级为 Step 6 轻量配置可用性保障；完整向导页留作后续可选项。
