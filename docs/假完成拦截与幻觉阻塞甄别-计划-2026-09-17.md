## 人话摘要

- **解决什么问题**：AI 代理节点两种"骗过编排器"的行为——① 一轮工具都没调用就谎称"缺工具/缺权限"停摆整条降级链（in6pe4qf 两次失败的直接原因）；② 活没干、文件没落盘，却申报完成，坑死下游节点（ai_client.dart 案例）。
- **做什么**：给 co-team 服务端加两道闸：未调工具的"缺工具"申诉按模型失败处理；节点完成前核查"规格点名的文件是否真的存在、是否零申报零改动"。
- **怎么做**：全部改动集中在 `server/src/orchestrator/orchestrator.ts`（加 `tool_rounds` 计数、降级链证据门、最终 JSON 闸产物核查）与 `server/src/types.ts`（观测字段），共 11 步。
- **做完后效果**：弱模型幻觉不再停靠人工门（自动换模型/自动重排）；"工作区连文件都没有就说完成"在节点完成前被拦截并给模型一轮真补齐的机会；补不齐判失败并写明原因。

## 1. 背景与目标

任务 in6pe4qf（D:\pxx\projects\learn-english，22 节点线性链）2026-09-16 两次失败于节点 3，均为：首选模型 deepseek-v4-pro 连续 429 被跳过 → 降级到本地小模型 nex-mini → 它零工具调用即输出"缺少只读侦查工具/写入权限"→ 文案命中 `LEGIT_BLOCKER_RE` → 降级链停摆、任务停靠人工门。同节点 deepseek 首轮工具调用实测返回 18KB 内容，证明"没工具"是幻觉。

同工作区历史（o3xmkraj）另有假完成实证：提交 93cf3c7 声称实现 `lib/services/ai_client.dart`，文件从未落盘入库，下游连续 5+ 轮死在同一 blocker。

**成功标准（可验收）**：
1. 零工具轮 + "缺工具/权限"类申诉 → 不停阶梯：同模型重试一次 → 再犯沉底换下一模型；全链耗尽 → error_type 走 infra 自动重排而非锁道。
2. 规格点名 `lib/...` 路径的节点，完成时文件不存在 → 修复轮让模型补齐 → 仍缺则节点 failed，error 含"产物核查未通过"。
3. 零申报 + 零实际改动 + 无豁免声明 → 同上拦截。
4. 既有 72 个 server 测试全绿；三端构建通过。

## 3. 方案与取舍

| 方案 | 做法 | 优点 | 代价/风险 |
|---|---|---|---|
| A（选定） | 产物核查放进 callAgent 最终 JSON 闸（修复轮机制内），阻塞甄别放进 dispatch 降级链 | 模型在失败前还有一轮机会真补齐/真调工具；复用既有机制，无新状态机 | 占用一个修复轮预算 |

## 9. 改前评审补充决策（2026-09-17 定稿，实施时直接照此执行）

实施前的全局引用检索与测试影响面核查结论（这些点原方案未定，现在已定）：

1. **作用域收窄到 `this.gitEnabled`**：产物核查门（3a+3b）整体以 `this.gitEnabled` 为前提，与 recordDeliveryCheck（:1868）的交付语义同源。已确认生产 `config.orchestrator.git: true`（config/config.yaml:162），**门在生产生效**；测试中只有显式 `gitEnabled: true` 的文件受影响——已核 `phantomGuard.test.ts` 两用例安全（其一 status:'failed' 天然跳过门、其二申报非空），实施步骤 8 跑全量后需复核 sandboxWorktree / branchWorkflow / resilience / snapshot / scaffold（它们用 simpleGit 但构造参数待确认）。
2. **`spec_missing` 放 AgentResult 顶层**（不放 delivery_check 内）：recordDeliveryCheck 在 :1889 整对象覆写 delivery_check，内嵌字段会被冲掉；顶层字段天然幸存，web/mobile 的类型镜像（web/src/api/index.ts:159）不感知，无 UI 改动。
3. **gate 只对成功申报执行**：`parsed.status==='failed'` 时跳过产物核查——模型已承认失败，不该被反向要求"补文件"。
4. **`classifyNodeError` 需显式映射两个前缀**：`假完成拦截` 与 `产物核查未通过` 必须判为 'content'——改动 5 引入 "'other' → infra 自动重排" 后，不显式映射会把这两类内容失败误自动重跑 3 次。
5. **`tool_rounds` 只计实际执行的工具轮**：末轮"模型仍要工具→强制终稿"的轮次工具并未执行，不计入——证据门只认"真拿到过工具结果"的会话，防弱模型空转骗过证据门。
6. **空申报守卫要兜住 midRunWritten**：轮内 write_file/edit_file 已写盘但最终 JSON 未申报的情形由 git 实际变更集兜住（actual.length>0 即不触发）；git status 失败时（actual=null）跳过 3b，仅保留 3a 的 fs 判定——非 git 目录不误伤。
7. **TOOLCLAIM_RE 窗口宽度**：须覆盖实测文案"本轮未获得任何文件系统读取、写入或命令执行工具"（申诉对象前 ≤20 字符），定为 `(未获得|无法获得|缺少|没有)[^\n]{0,20}(工具|权限)` + `只读侦查|cannot (call|use) tools` 等英文分支。
8. **单测避开 429 退避**：CAPACITY 分支的退避是真实 `setTimeout(20s/40s)`（:2869），429 用例会拖慢套件——error_type 用"连接错误全灭 → 'other'"路径验证，覆盖同一落点。
9. **实施发现的其余事项**：生产构造在 `server/src/index.ts:186`（`gitEnabled: config.orchestrator.git`）；多数测试用 `makeOrchestrator()` 辅助函数，其 gitEnabled 缺省值在实施步骤 7 前逐一确认。
