- 测试日期：2026-09-06
- 测试人：独立开发者角色（模拟真实用户全流程）

## 二、问题清单

### P0（影响可用性/可信度，建议优先修复）

**#1 上游模型持续 504 未熔断，模型池健康度失真**
- 现象：glm-5.3-flash（tokenrhythm 上游）自 08:13 起多次 `504 Gateway Time-out`（alb 网关），Agent dispatch 反复失败重试；日志证据 `Agent dispatch failed ... 504 ... alb`（00:13:35、00:31:00 等）。但 `/api/status` 中该模型 `healthy: true` 始终不变。
- 影响：每次派发都先撞一次 504 再 fallback，节点执行被拖长（节点 1 耗时 1037s，主要落在慢速 LAN 模型 gemma-4-31b-it）；规划阶段同样受累（一次小任务规划耗时 4 分钟）。整任务 ETA 显示 7259 秒（约 2 小时）。
- 建议：将连续派发失败（如 5xx ≥2 次）联动 healthy 标记并临时摘除/降权，恢复探测后再回池；504 重试加退避上限。

**#2 服务级整站冻结约 11 分钟**
- 现象：00:16:05 后日志完全无输出，`/api/status` 等全部 HTTP 请求挂起（curl 20s 超时），约 00:27 自行恢复且任务继续执行（node 1 于 00:27:45 完成）。冻结窗口与 Agent 节点执行中段重合。
- 影响：整个看板/API 假死，用户在 UI 上表现为"全部卡死"。
- 备注：测试实例代码包含并行会话未提交的 RAG 半成品（embeddings.ts 新增、llm/knowledge 改动），不排除根因在未完成代码；但该窗口内事件循环被阻塞的症状明确（此前 17 分钟的节点执行期间 API 一直正常，说明是特定操作触发）。建议加事件循环阻塞监测（如 perf_hooks monitorEventLoopDelay）定位阻塞点。

**#2b 派发时确定性崩溃：`ENOTDIR: not a directory, scandir '…\app\main.py'`（测试中后期新发现）**
- 现象：HR 任务节点 6（test）多次派发直接失败，报 `ENOTDIR: not a directory, scandir 'C:\Users\nw02\AppData\Local\Temp\coteam-sbx-Rf1yld\app\main.py'`（01:27:54、02:09:49 两次观测）。沙箱内 `app/main.py` 本身是正常文件——是服务端某处把"文件路径"当作目录去扫描。
- 影响：该错误每次派发必现，等于节点 6 的部分重试预算被一个与需求无关的服务端 bug 烧掉；test 节点自 01:16 起重试循环超 1.5 小时（retry_count=4、派发 12+ 轮），是"流程卡住"的直接原因之一。
- 建议：排查 dispatch 链路中的目录扫描/复制逻辑（scandir 调用点不在 sandbox.ts，需定位）；对文件/目录类型做防御。

### P1（体验/一致性，尽快修复）

**#3 任务创建为同步长请求，UI 无阶段性反馈**
- 现象：`POST /api/tasks` 在一个 HTTP 请求内完成需求评估+规划（实测 38s～4.5 分钟，取决于上游模型）；Web 端仅显示"提交中..."按钮 spinner，无阶段/进度提示。
- 影响：用户面对 4 分钟无响应的按钮，极易重复点击或认为已失败；长请求也易被网关/重启打断（与 #5 叠加时直接丢失）。
- 建议：拆成"创建任务（秒回 task_id）+ 异步规划 + WS 推送规划进度"，或至少分阶段提示（正在评估需求→正在生成计划）。

**#4 任务中心统计口径与列表口径不一致**
- 现象：任务中心表格默认 `scope=external`（仅列无项目的临时任务，useDashboard.ts:41 默认 taskFilter），而统计 chips 与"共 N 个任务"请求不带 scope 统计所有任务。实测：项目任务执行中时，页面显示"共 1 个任务/执行中 1"，但表格 0 行"暂无任务"，该任务仅出现在队列面板。
- 影响：用户会误以为任务丢失；项目任务在任务中心完全不可见、不可点入详情。
- 建议：统计与列表同口径，或提供"项目任务/临时任务"切换，把项目任务纳入任务中心列表（至少可查看）。

**#5 dev 模式 tsx watch 重启会无声杀掉进行中的请求与规划**
- 现象：测试期间并行会话修改 `server/src/*.ts` 与 agents 配置触发 tsx 重启（日志 `tsx] change in ./src\llm.ts Restarting...` 等），两次进行中的 `POST /api/tasks` 请求直接失败且任务未持久化（不在任务列表）。
- 影响：开发期修改配置/代码 = 正在执行的请求与规划全部丢失，无重试/幂等保护。
- 建议：任务创建幂等化（客户端重试安全）；文档明确生产用 `node dist` 或无 watch 模式。

**#6 执行期间用户工作目录为空，进展不可见**
- 现象：沙箱开启（config sandbox: true）时，Agent 在 `Temp/coteam-sbx-*` 副本内工作，每个节点在沙箱 git 提交；真实工作目录 `D:/pxx/hr-system` 在任务完成合并前保持空目录（src/tests 为空）。
- 影响：用户在 IDE 中看不到任何产出，"系统到底有没有在干活"只能依赖看板；若任务中途失败，用户对沙箱内成果无感知。
- 建议：看板任务详情展示沙箱路径与节点级 diff；文档说明合并时机；或提供节点完成后同步预览。
- **关联 #15（更严重）**：任务失败时已完成节点成果根本不回写，沙箱无恢复入口，见附录。

**#6b agent.yaml 的 timeout 配置是死配置，LLM 调用超时失控**
- 现象：`agents/*/agent.yaml` 的 `timeout: 300` 被加载（agents.ts:62）但全代码库无消费点；`llm.ts` 的 chat() 支持 AbortSignal 但无人传业务超时。实测存在一个事实上的 ~32 分钟超时（gemma-4-31b-it 两轮分别于 01:35→02:08、04:47→05:19 生成 33/32 分钟后以 "Request timed out" 失败，疑似 HTTP 客户端默认值），远超合理范围且不可配置、不可观测。
- 影响：慢/挂起的模型轮次最多可拖 32 分钟才失败；任务 ETA 完全失控（本任务节点 6+7 合计在重试上消耗 2 小时+）。
- 建议：LLM 请求默认超时（可配置，按 agent.timeout 覆盖）+ 单节点总时长上限告警。

**#6c 重试预算与配置不符、内容性失败与网络失败混为一谈**
- 现象：config `max_retries: 3`，实测节点 6 retry_count 已达 4（派发 12+ 轮仍未终止）；且"模型拒绝执行（如：素材不足无法分析）"、"输出解析失败"、"上游 504"都被当作同类失败进入模型轮换重试。对照：README 辅任务的节点 1 同样轮换 9+ 次模型、耗时 45 分钟，最终第 3 次尝试才成功。
- 影响：注定失败的节点要烧完整个轮换预算（每次 1~3 分钟 LLM 调用）才停止，成本高、等待久；模型明确回复"需要人类补充 X"时，系统没有把这类信号升级为 clarify/人工介入。
- 建议：区分失败类型（网络错误→快速重试/摘除；内容性拒绝→升级 clarify 或直接终止）；重试预算计数修正并与 max_retries 对齐。

### P2（细节/打磨）

**#7 项目办公区 dev Agent 头像字母错误**
- 项目开发 → 办公区中 dev 显示为 "DE"，与 deploy 相同；工作台则正确显示 "DV"。两处取首字母逻辑不一致。

**#8 `POST /api/tasks` 不校验 project_id 存在性**
- 传入不存在的 project_id 静默成功，任务挂在"幽灵项目"上（移动端/项目页永远 0 任务）。建议 404 校验或自动建项目。

**#9 模型池测试接口要求传完整凭据**
- `POST /api/config/model-pool/test` 必须带 name+api_key+base_url，仅传已存在模型的 name 报 400"需要 name, api_key, base_url"。UI 若只传 name 将无法使用（本次未验证 UI 路径）。

**#10 中文 Windows 下控制台创建任务会存储乱码**
- 历史通过 CLI/控制台创建的任务描述在 API 返回中为 GBK 乱码（"?? һ??????"）；经 API/Web 创建的 UTF-8 内容正常。输入源编码应统一转 UTF-8。

**#11 favicon 404 噪音**
- 日志周期性出现 `GET /favicon.ico 404`，建议静态托管补一个图标。

**#12 技能自动匹配存在误注入**
- 现象：docs Agent 的"撰写 README"节点被自动注入了 `vue3-crud-scaffold`（日志标记 `vue3-crud-scaffold(keyword)`）——这是一个 Vue3 前端 CRUD 脚手架规范技能，与文档任务无关。原因是技能 tags/描述与节点名的 CJK 二字词/关键词重叠即命中（MAX_AUTO_SKILLS=2）。
- 影响：无关技能白白占用上下文（最多 2000 字符/条），可能干扰小模型输出格式。
- 建议：自动匹配提高阈值或仅按 tags 精确匹配；keyword 通道要求更强的词面证据。

**#13 交付申报率低是普遍模式（质量闭环高频告警）**
- 现象：节点 1、节点 5、节点 6 三次交付都被 `Delivery consistency check` 标记大量未申报文件（unreported:9 / unreported:12 / unreported:14），并两次触发 SSOT 文档自动恢复。质量闭环兜底有效，但 dev/test 提示词中的交付申报契约没被模型稳定遵守。
- 建议：把"交付必须申报文件清单"做成 harness 层硬约束（从工具调用记录自动推导，而非依赖模型自述）。

**#14 队列 API 对不存在的 key 返回 200 并伪造空队列**
- 现象：`POST /api/queues/nonexistent/resume|clear` 返回 200 + 一个凭空构造的空队列快照，而非 404。
- 影响：调用方无法区分"恢复成功"与"key 写错"；可能掩盖真实排队状态。

## 三、执行最终结果（附录）

**README 辅任务（o45zgbpf，Web UI 提交）：success ✅（含完整失败→重试→成功→合并闭环）**
- 节点 1 因"工作区为空 + 描述中的路径在沙箱外被拒"轮换 3 个模型失败 2 轮后第 3 次尝试成功；后续 3 节点一次通过；merge-auto 把 README.md 合并回 `D:/pxx/hr-docs-scratch` 并以 `coteam: task o45zgbpf auto-commit` 提交，任务分支 `coteam/task-o45zgbpf` 留在工作区。
- 回写验证：✅ 文件真实落盘且内容合理。

**HR 主任务（1j9kibih）：failed ❌（6/8 完成后于节点 7 终止）——失败路径完整验证**
- 节点 1~6 全部完成（dev：数据模型/登录、员工部门 API、请假审批逻辑；test：三类验证），交付报告均可查询。
- 节点 7（dev 前端页面）重试耗尽后失败，最终错误：`all models failed (2 tried): result schema violations: verification 必须是非空字符串`——模型反复产出不合结果 schema 的输出（另有多次 JSON 解析失败、一次 32 分钟超时）。
- 节点 8 与 merge-auto 正确级联取消；任务状态 failed。
- **失败处理验证 ✅**：队列按设计阻塞（`任务 1j9kibih 执行失败…请处理后手动恢复`），控制台通知发出，`POST /api/queues/:key/resume` 手动恢复成功。
- **失败处理缺陷（#15）**：已完成的 6 个节点成果**没有合并回工作区**——`D:/pxx/hr-system` 仍在 master 且只有 scaffold 提交，src/tests 为空；全部代码只存在于临时沙箱 `Temp/coteam-sbx-Rf1yld`（未清理但也无任何 UI/API 指引可找回）。用户视角：跑了 3 小时、完成 75% 的节点，工作目录里什么都没有。

**#15 任务失败时已完成节点的成果不回写、沙箱无恢复入口**
- 现象：如上。merge-back 只在任务成功时执行（对照 README 任务 success 后正常回写）。
- 影响：部分成功的长任务（现实中最常见）其已验证成果对用户完全不可见；沙箱目录位于系统临时目录，可能被系统清理，成果存在丢失风险。
- 建议：任务终态为 failed 时，把已完成且通过验证的节点成果合并回工作区（或提供一键"导出已完成成果"）；至少在任务详情中展示沙箱路径与恢复指引。

**环境备注（非产品缺陷）**：测试期间另一会话在 `server/src` 重构 metrics（metrics.ts→metrics/），导致测试实例 `/api/metrics`、`/api/metrics/trend` 500（ERR_MODULE_NOT_FOUND）；两个服务实例共用同一份源码所致，看板"运行指标"面板报错属于该并行改动波及。
